# Hardset — supersets and drop sets

Two shapes the logger could not record. Both are **the lifter arranging their own work**, and both
change exactly one thing about the app's behaviour: *when the rest timer is armed*.

That sentence is the whole design, and it is what makes them permissible in an app that refuses to
prescribe. Nothing here picks a pairing, a drop percentage, a rest length or a set count. Compare
`docs/SPLITS-spec.md` §1: the app may arrange what the lifter already does; it may not decide how
much of it they do.

---

## 1. What each one is

**A superset** is two or more movements taken back to back, with the rest moved to the end of the
round. In storage it is a number on `sessionExercises`; on screen it is a letter.

**A drop set** is a working set continued at a reduced load with no rest in between. In storage it
is a flag on `loggedSets`; on screen it is an arrow instead of a set number, and an indented row.

**Myo-reps and cluster sets are refused.** They need genuine sub-set structure with intra-set rests,
which means a nested model and a second concurrent AlarmKit alarm. `docs/research/r3-research.md:92`
reaches the same conclusion and suggests representing them as a plain set sequence with a short rest
override, which remains available and costs nothing.

## 2. The one rule

`SupersetRest.shouldArmRest(afterLogging:in:session:)` in `HardsetCore`. Pure, Foundation-only, no
database handle — the same rule `PriorPerformanceSnapshot` and `SplitDealer` follow. Every condition
lives here rather than accumulating in `SessionCoordinator.logSet`:

1. A **warm-up** arms nothing. Unchanged.
2. A set with a **drop queued behind it** arms nothing. Read off the *next* row, so it holds for a
   chain of any length and for the last link, which does arm.
3. Inside a **superset**, a set arms nothing until every other member has either logged at least as
   many working sets, **or has no work left**.
4. Otherwise, it arms.

**Clause 3's second half is load-bearing.** Without it, a partner with fewer sets blocks rest
permanently once it is finished: pair a 4-set movement with a 2-set one and the last two sets of the
longer movement never start a timer. `finishedPartnerDoesNotBlock` pins it.

Rounds are counted in **working sets**, so a drop inside a superset does not advance the round.

## 3. Counting

**A drop adds no set.** It is counted as part of the set it continues.

This is an **adopted convention with no finding behind it**, held to exactly the standard
DECISIONS #17 holds the 0.5 indirect credit to. No convention for counting drops is established; the
fractional scheme in use was fitted to studies of conventionally performed sets. The only ground
claimed is that it is the reading which cannot manufacture volume — counting each drop separately
reports three sets dropped twice as nine, and every weekly figure inflates the moment anyone uses
the feature.

`SetCounting.dropSetConvention` carries the text, it is interpolated into
`SetCounting.source.methodology` so the App Review 1.4.1 disclosure is generated by the same code
that does the counting, and `dropConventionIsDisclosed` asserts it keeps saying so — including that
it is "not a judgement" about the technique. *The app will not report this as a set* and *this is
worth less than a set* are different statements, and only one of them is supportable.

**Tonnage is unaffected**, because tonnage is arithmetic rather than convention. Every drop's load
and reps count in full. `SessionVolume.dropSets` reports them separately for the same reason
warm-ups are reported separately: work that vanishes from a summary reads as a bug.

### The three read paths that had to learn this

Excluding drops matters most where it is least visible:

| Path | Why |
|---|---|
| `priorPerformanceSnapshot` | **The dangerous one.** A drop is the lightest load of the session by construction. Leaving drops in hands next week's opening row the bottom of last week's chain — a suggestion that gets *lighter* every time the lifter trains hard. |
| `completedSets` | Record detection. A deliberately reduced load is not a benchmark, and letting one set the bar would make the margin rule fire against a number the lifter never treated as a working set. |
| `ProgressionStore.samples` | The chart plots a session's best work. A drop is neither a heaviest load nor an estimable one-rep max. |

## 4. Schema

Added to the **v1 migration**, not a v2 — nothing has shipped and no build has reached a device, so
v1 is still one designed artefact and this is the last free moment to reconsider a column.

```
sessionExercises  + supersetGroup INTEGER          (nullable)
loggedSets        + isDropSet     INTEGER NOT NULL DEFAULT 0
```

**`supersetGroup` is a plain number and not a foreign key.** A superset has no existence outside the
workout it is performed in, so there is no row for it to reference. It is never shown; the UI
derives a letter from position within the group.

**`isDropSet` sits beside `isWarmup` rather than replacing both with one `kind` column.** `isWarmup`
predates this and is filtered on in SQL in half a dozen places. `SetKind` in `HardsetCore` is the
write-side type, and it is the only thing that produces the pair — which is what keeps "a warm-up
that is also a drop" from ever being written. `STRICT` tables forbid `CHECK`, so that constraint
cannot live in SQL and has to live in a type.

`SetKind.init(isWarmup:isDropSet:)` **resolves** the impossible combination instead of throwing,
unlike `RestTimerState`. The difference is what the caller could do about it: a corrupt rest timer is
one device's transient state, while this decode sits on the crash-recovery path where throwing would
take a whole workout's written sets down with one bad row. It reads as a warm-up — the reading that
cannot inflate anything.

**Deliberately not modelled:** `amrap` and `backoff`. `docs/research/r3-research.md:138` recommends
adding them now so a later release is "a UI change rather than a migration". DECISIONS #4 runs one
way — a column may be added at any time and never removed — so an unbuilt case defers for free while
a guessed one commits the schema to a vocabulary no screen has been designed against.

## 5. What the corpus got wrong, and why it does not apply

`docs/research/r3-research.md:91` recommends shipping supersets in v1 but holding drop sets to 1.1,
because "auto-advance blocks adding drop sets" — the specific complaint logged against Alpha
Progression in `prior-research.md:798`.

**Hardset has no auto-advance.** `grep -n "autoAdvance"` over `Packages/HardsetKit/Sources` returns
nothing, and the log control acts on `nextUnloggedSlotID` without ever moving focus. The objection is
against a feature this app does not have, so both ship together.

## 6. UI

- A **letter chip** on the movement header (`Superset A`), derived by `SupersetGrouping.letter` in
  `SessionView`, which is the only layer that can see the whole session.
- Grouping joins a movement with **the one after it**, which keeps a group contiguous by
  construction. A superset scattered down the screen is a scrolling problem during the part of a
  workout where scrolling is hardest, and nothing in the rule needs adjacency — so the constraint
  costs nothing and buys the ordering. Joining again extends the group to a third movement.
- Leaving a pair **ungroups the movement left behind**. A group of one is not a superset, and the
  survivor would otherwise stay lettered while the rest rule waited for a round that cannot complete.
- **No container is drawn around the pair.** A card wrapping two movements is a layout the logger
  does not otherwise have, and the fact the lifter needs is small. The behaviour is the feature.
- A **`Drop` button** beside `Add set` and `Warm-up`, shown only when there is a row to continue.
- A drop row is **indented** and badged `↓` rather than numbered, because it has no number of its
  own — numbering it would print the very inflation the counting convention exists to avoid.
- A drop **seeds its load from the row above and leaves reps empty**. The app has no established
  reduction percentage; seeding the parent's load makes the reduction an edit the lifter makes.

## 7. Scope

Still out, and deliberately:

- **Motion.** No new animation. The four hero moments stay behind the device gate per HANDOFF §8.
- **Supersets in a split.** `splitEntries` gains no grouping column in this pass. A split is a
  partition across days; a superset is an arrangement within one workout. Additive later if asked.
- **A learned rest default.** See DECISIONS #27 — the app records finish-to-finish intervals, not
  rest, and the difference is the set itself.
