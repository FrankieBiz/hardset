## Elos Train: ruthless carry-forward / rebuild / drop inventory for the new standalone science-based lifting app

**Summary.** Elos Train has exactly four genuinely differentiated ideas, and one of them is 94% non-functional in the shipped app.

The real assets: (1) machine identity recorded per set (`ExerciseSetRecord.equipmentDedupeKey/equipmentBrandName`, ElosSchema.swift:191-193) with PR and overload grouping scoped to that machine (StrengthMath.swift:23-30); (2) a per-gym inventory with provenance ranking and a hard "empty means unknown, never empty gym" invariant (GymInventory.swift:123-153, GymEquipmentLearning.swift:53-78); (3) per-gym day variants of the same split with a before/after diff preview on gym switch (DayVariants.swift:29-36, GymSwitchPreview.swift) — undocumented in the prior competitive research and, as far as that research shows, uncontested; and (4) muscle attribution captured at log time per set (`muscleTargetsJSON`, ElosSchema.swift:213) so brand machines are not lost to a name join, which is precisely the failure the server has (LoggedVolumeAnalyzer.swift:5-15).

The killer defect: the join between the 404-entry exercise catalog and the 1,697-record equipment DB is broken. `EquipmentDatabase.variants(forExercise:)` (EquipmentDatabase.swift:1735-1743) yields a machine list for only **23 of 404** catalog exercises; only **398 of 1,616** training-relevant equipment records are reachable from any catalog name. `GymMachineBinder` binds only **21 of 404**. There are 83 "Chest Press" machines in the DB and the catalog calls it "Seated Chest Press Machine", so it matches none. This is the same vocabulary-mismatch bug `GymEquipmentTaxonomy` was written to fix (GymInventory.swift:51-59), recurring in a second place, uncaught.

Worse, the escape hatch makes the score lie. Picking a raw machine names the exercise "Panatta Leg Extension" (ExercisePickerView.swift:739-746), which resolves to no catalog candidate, so `isCompound` is false (ScoredExercise.swift:88-90) and every scorer takes its neutral fallback — the flagship feature is the fastest route to the 78/100 "Dialed in" false positive.

Drop, without sentiment: XP/ranks (GamificationEngine.swift:8-45), the SplitFinder quiz + 419-line hardcoded recommender, InjurySubstitutionEngine (hardcoded 1:1 name map, medical exposure), community splits, stretch routines, and the dead E1RMCalculator. Rebuild the equipment model as a crowd-sourced per-gym registry; a fixed 19-brand literal cannot cover a real gym floor.

Getting from 23 to 404 exercises with machine variants requires a curated movement-key mapping across 1,616 equipment records and 404 exercises — a labeling task, not an algorithm, and one a solo developer will be tempted to shortcut with exactly the substring heuristic that failed twice already (GymEquipmentTaxonomy's comment and variants(forExercise:)).

## iOS 26 platform capabilities for a greenfield science-based lifting app (Swift 6.3 / Xcode 26.4, min deployment iOS 26.0)

**Summary.** The single biggest platform finding is that the rest timer — the feature competitors lose stars over — should not be built on ActivityKit at all. iOS 26 shipped **AlarmKit**, whose `AlarmManager.AlarmConfiguration.timer(duration:attributes:stopIntent:secondaryIntent:sound:)` gives you a system-owned countdown with Lock Screen + Dynamic Island + StandBy + Apple Watch presentation, pause/resume/cancel, and an alert that breaks through silent mode and Focus. Its `AlarmAttributes` literally conforms to `ActivityKit.ActivityAttributes`, so you get the Live Activity for free, driven by `fireDate` rather than by pushes — meaning zero consumption of the opaque ActivityKit update budget. Elos's current rest notification (`NotificationManager.swift:83-95`) is a plain `UNTimeIntervalNotificationTrigger` with `sound = .default` and no `interruptionLevel`, so a Focus mode silences it. That is the exact failure competitors get reviewed for, and AlarmKit removes it with roughly 150 lines.

Second: **Foundation Models is a trap if used as a calculator and a genuine asset if used as a renderer.** The SDK hardcodes `contextSize` to `4096` and back-deploys it as a literal; the framework is `@available(watchOS, unavailable)`; and it is gated on Apple-Intelligence-eligible hardware (A17 Pro / 8 GB, iPhone 15 Pro+), a strict subset of your iOS 26 floor. Every numeric claim must come from your pure engine; the model's only safe jobs are prose explanation of engine output and natural-language intake, with `@Generable` + `Tool` used so the engine, not the model, does arithmetic.

Third: **Liquid Glass is cheap but has one hard structural rule** — glass cannot sample glass, so the floating rest bar + log-set control + tab bar must live in one `GlassEffectContainer`. `Glass.identity` is the correct conditional-off value; accessibility adaptation is automatic and must not be overridden.

Fourth, three quiet wins: `HKWorkoutSession(healthStore:configuration:error:)` is `API_AVAILABLE(ios(26.0))` — iPhone can finally own a workout session and stay alive in the background without a watch; `tabViewBottomAccessory` + `tabBarMinimizeBehavior(.onScrollDown)` is a purpose-built slot for a workout-in-progress mini bar; and Swift's concurrency defaults are **off** in the build system (`SWIFT_DEFAULT_ACTOR_ISOLATION = nonisolated`, `SWIFT_APPROACHABLE_CONCURRENCY = NO`) — you must set them explicitly on day one, not later.

iOS 26 sat at 85.12% (TelemetryDeck, end of July 2026) and iOS 27 ships ~mid-September 2026, so a min-26 floor is defensible.

### Findings
- **AlarmKit — not ActivityKit — is the correct primitive for the rest timer, and it hands you the Live Activity for free.** _(high)_
  - detail: From the on-disk iOS 26.4 SDK: `AlarmKit.AlarmManager.AlarmConfiguration.timer(duration: TimeInterval, attributes: AlarmAttributes<Metadata>, stopIntent: (any AppIntents.LiveActivityIntent)? = nil, secondaryIntent: (any AppIntents.LiveActivityIntent)? = nil, sound: ActivityKit.AlertConfiguration.AlertSound = .default)` (AlarmKit.swiftinterface:258), scheduled via `schedule(id:configuration:) async throws -> Alarm` (:262), with `countdown(id:)`, `cancel(id:)`, `stop(id:)`, `pause(id:)`, `resume(id:)` (:263-267) and an `alarmUpdates: some AsyncSequence<[Alarm], Never>` feed (:271). Critically, `public struct AlarmAttributes<Metadata> : ActivityKit.ActivityAttributes` (:16) — the ContentState is `AlarmPresentationState`, whose `.Mode.Countdown` carries `totalCountdownDuration`, `previouslyElapsedDuration`, `startDate`, `fireDate` (:92-105). You get separate `AlarmPresentation.Alert` / `.Countdown` (with `pauseButton`) / `.Paused` (with `resumeButton`) presentations (:41-90). Authorization is `AlarmManager.shared.requestAuthorization() async throws -> AuthorizationState` (:277) plus an `NSAlarmKitUsageDescription` Info.plist string. No entitlement file is required (grep of the SDK framework bundle found no entitlement key).
  - evidence: /Applications/Xcode.app/Contents/Developer/Platforms/iPhoneOS.platform/Developer/SDKs/iPhoneOS26.4.sdk/System/Library/Frameworks/AlarmKit.framework/Modules/AlarmKit.swiftmodule/arm64e-apple-ios.swiftinterface:16,41-105,256-277
  - implication: Build the rest timer as an AlarmKit countdown, not as a hand-rolled `Timer.publish` + `Activity.request` + `UNNotificationRequest` trio. One API replaces all three, and the widget extension renders `AlarmAttributes<YourMetadata>` via a normal `ActivityConfiguration`. Budget ~150 LOC plus a widget extension target, not the ~600 LOC a hand-rolled equivalent costs.
- **AlarmKit alarms break through silent mode and Focus; Elos's current rest notification does not, and that is a concrete competitor-grade defect.** _(high)_
  - detail: WWDC25 session 230 states AlarmKit alarms "break through silent mode and focus," and positions the framework for user-initiated timers (cooking, travel) while explicitly saying it is "not a replacement for critical alerts or time-sensitive notifications." By contrast Elos schedules `UNMutableNotificationContent()` with `content.sound = .default` and a `UNTimeIntervalNotificationTrigger`, setting no `interruptionLevel` (so it defaults to `.active`), which any Focus mode or the ring/silent switch suppresses. A gym is exactly where a lifter has Focus on and the phone face-down.
  - evidence: /Users/frankbisignano/dev/elos/apps/elos-mobile/Elos/Elos/Utils/NotificationManager.swift:83-95 ; https://wwdcnotes.com/documentation/wwdc25-230-wake-up-to-the-alarmkit-api/ ; https://developer.apple.com/videos/play/wwdc2025/230/
  - implication: A rest timer that is inaudible under Focus is the single most reviewable defect in this category. AlarmKit removes it categorically; the fallback (if AlarmKit authorization is denied) is a `UNNotificationContent` with `interruptionLevel = .timeSensitive`, which requires the Time Sensitive Notifications capability. Plan for both paths and for the denied-authorization state.
- **The countdown UI in a Live Activity must be system-rendered via `Text(timerInterval:)` / `ProgressView(timerInterval:)`, which costs zero updates and survives backgrounding by construction.** _(high)_
  - detail: SDK signatures: `Text.init(timerInterval: ClosedRange<Date>, pauseTime: Date? = nil, countsDown: Bool = true, showsHours: Bool = true)` (SwiftUICore.swiftinterface:7497) and `ProgressView.init(timerInterval: ClosedRange<Date>, countsDown: Bool = true, ...)` (SwiftUI.swiftinterface:1241-1249). The `pauseTime:` parameter is the mechanism for a paused rest timer — you do not stop updating, you hand the system a freeze point. Elos already learned the underlying lesson the hard way: ActiveSessionView.swift:17-19 documents that it stores an absolute end date rather than decrementing a counter, "because a `Timer.publish` tick doesn't fire while backgrounded."
  - evidence: SwiftUICore.swiftinterface:7497 ; SwiftUI.swiftinterface:1241-1249 (iPhoneOS26.4.sdk) ; /Users/frankbisignano/dev/elos/apps/elos-mobile/Elos/Elos/Views/ActiveSessionView.swift:17-19
  - implication: Store `restEndsAt: Date` as the canonical rest state everywhere — engine, SwiftData, widget, watch — and never a remaining-seconds Int. ### Risks
- AlarmKit is a young framework (iOS 26.0, with a deprecation already landed at 26.1 — `AlarmPresentation.Alert.stopButton` is deprecated in favor of the newer init). Building the app's most critical feature on it means inheriting its bugs and its API churn, and there is no fallback that delivers Focus-piercing alerts without it. Mitigate by keeping the timer behind an internal protocol so a UNNotification-based implementation can be swapped in.
- Apple Intelligence eligibility (A17 Pro / 8 GB, iPhone 15 Pro+) is a strict minority of the iOS 26 install base. Any product positioning, screenshot, or paywall copy that leans on the on-device LLM will misfire for most users. If the coach explanation becomes a headline feature, the app effectively raises its hardware floor without saying so.
- The 4,096-token context window has not moved across three point releases (26.0 → 26.4) despite a full model-generation refresh in June 2026. Planning for it to grow is unsafe; any design that needs conversational memory of a training history is not buildable on-device today, and there is no Private Cloud Compute path for third-party apps.
- Liquid Glass cannot be validated in the Simulator, and this environment additionally cannot run tests under sandboxed xcodebuild without a pty. That means the app's most visually distinctive layer has the weakest automated verification story — a real risk for a solo dev shipping async.
- Glass GPU and battery cost is real (one report: 13% vs 1% for a continuously animated screen) and a lifting app is a long-running foreground session on a phone that may already be warm. Thermal throttling mid-workout would surface as timer jank at exactly the worst moment.
- `tabBarMinimizeBehavior(.onScrollDown)` has a reported failure to trigger inside tabs using `NavigationStack(path:)` — which is the standard navigation pattern. If the workout mini-bar is architecturally dependent on the accessory + minimize behavior, this bug can force a layout redesign late.
- Guideline 4.3 was expanded in 2026 to reject apps 'indistinguishable from what's already widely available,' and workout loggers are a saturated category. The science engine is the differentiator, but App Review sees the logging UI first. A thin-looking v1 that leads with a timer risks a 4.3 rejection.
- Since April 28 2026 every submission must build against the iOS 26 SDK. That is satisfied here, but it also means Apple can force an SDK bump annually; any dependency on iOS 26-specific rendering behavior (glass sampling, tab accessory geometry) may shift under iOS 27, which refines rather than replaces Liquid Glass.
- AlarmKit's own framing is 'user-initiated timers, not a critical-alert replacement.' I found no App Review restriction and no entitlement requirement, but I also found no authoritative statement clearing a fitness rest timer specifically. If review takes a narrow reading, the Focus-piercing behavior could be challenged.
- Adding a widget extension, a HealthKit entitlement, App Intents, and (later) a watchOS target multiplies the build/test matrix for one person on a 16 GB M3 Air. Each new target is another place for a signing, entitlement or App Group misconfiguration to silently break a shipped feature.

### Open questions
- Is a native watchOS app in scope for v1, or is the AlarmKit + `.supplementalActivityFamilies([.small])` mirrored presentation sufficient? Mirroring gives a credible watch presence for near-zero cost, but it cannot log a set from the wrist or read heart rate — that requires a real watchOS target and roughly a quarter of additional work.
- Should the on-device LLM ship in v1 at all, or wait for v1.1? Shipping it later removes the eligibility-messaging problem from launch entirely and lets the engine prove itself first; shipping it at launch is the more distinctive story but adds three UI states and a whole error-handling surface.
- Is HealthKit integration a v1 requirement? It unlocks iPhone-side `HKWorkoutSession` (background execution, OS-authoritative session duration) which has architectural value beyond the Health write itself — so the answer may be yes for reasons unrelated to Health data.
- What is the minimum hardware you will physically test on? Glass and thermals cannot be validated in the Simulator, and iPhone 11 is the iOS 26 floor. Owning or borrowing an older device changes what 'verified' means for the whole design layer.
- Does the workout screen use the tab-view bottom accessory as its primary composition, or a full-screen logger? This decision cascades into navigation structure, the GlassEffectContainer hierarchy, and whether the reported `.onScrollDown` + `NavigationStack(path:)` bug is on the critical path.
- Do you want AlarmKit's Focus-piercing behavior as the default, or opt-in? It is the right default for a gym, but a timer that overrides Do Not Disturb without the user expecting it is also a support complaint waiting to happen.
- Should the engine live in a separate Swift package from day one (nonisolated, Foundation-only, its own test target) even though there is only one app? It costs a little ceremony now and is the difference between a testable engine and another 18k-line feature folder later.

## Backend v2 architecture for the new standalone science-based lifting iOS app (greenfield, iOS 26, solo dev)

**Summary.** Start fresh. The existing `elos-api` is 5,029 lines of TypeScript across 13 services and 15 routers with 38 migrations (2,192 lines), and essentially none of it is an asset for the new app: roughly two-thirds of the migration volume is exercise/equipment/how-to seed *data* (016, 021, 032, 036, 037, 040) that should be copied as a versioned CDN blob rather than as schema; the shared contract package is dead (packages/elos-shared/src/index.ts declares `LoginRequest {email,password}` for a custom-auth design that was abandoned in favor of Supabase); and every structural fix the prior audit recommends — sync columns on every table, JSONB instead of TEXT program blobs, per-(user,app) `is_active`, `/v1` versioning, a squashed baseline, a real SQL test harness — sums to a rewrite. The new app has zero users, so migration cost is zero. Forking buys you a maintenance obligation to a second release train and nothing else. Copy ~200 lines (`lib/query.ts`, `lib/httpError.ts`, `middleware/validate.ts`, the pino redaction list at `lib/logger.ts:5-14`, the advisory-locked `migrate.ts`) and the catalog data. Write the rest.

Technology: Hono on Node 24 (or Bun), raw `pg` with a Testcontainers harness, Postgres 18 on Render or Neon. At this app's traffic — local-first, ~87 sync calls per user per month — framework throughput is irrelevant; the decisive differentiator is that Hono + `@hono/zod-openapi` emits an OpenAPI 3.1 document that Apple's swift-openapi-generator 1.12.2 turns into compile-checked Swift DTOs, closing the contract gap that let `session_rpe: 0` ship (schemas.ts:8 allows 0; migrations/004_create_workout_sessions.sql:6 forbids it). Infra runs $13/mo at 1k users, ~$60 at 10k, ~$400 at 100k.

The load-bearing design decision is the sync cursor. Do **not** use `updated_at`: `now()` returns transaction-start time, so overlapping transactions can commit out of timestamp order and a client that advances past the later timestamp permanently misses the earlier row. Use a per-user `bigint` sequence incremented by `UPDATE sync_state ... RETURNING`, which holds a row lock to COMMIT — making seq order identical to commit order, gap-free, and serialized per user only.

Auth: Sign in with Apple only, no account required before first value, your own session tokens. Entitlement: point App Store Server Notifications v2 at RevenueCat, consume RevenueCat webhooks into your own `subscription` table so you own the data if you ever leave.

### Findings
- **Start fresh: the existing elos-api contains almost no reusable application code, and its only genuine asset is seed data that should not live in migrations at all.** _(high)_
  - detail: `find src -name '*.ts' | xargs wc -l` totals 5,029 lines across 13 services and 15 routers; `ls migrations/*.sql | wc -l` returns 38 files totaling 2,192 lines, of which the catalog seeds (016_seed_exercise_catalog, 021_seed_cable_freeweight_expanded, 032_fix_cable_exercise_equipment, 036/037 howto, 040_fix_exercise_muscle_attribution) are the bulk. The shared contract package is dead code: packages/elos-shared/src/index.ts declares `LoginRequest {email: string; password: string}` and `RegisterResponse {token, user_id}` describing an abandoned custom-auth design, while the live API authenticates via `supabaseAdmin.auth.getUser(token)` (src/middleware/auth.ts:54). Migration numbers 022 and 029 were never committed. The reusable code is ~200 lines: src/lib/query.ts, src/lib/httpError.ts, src/middleware/validate.ts, the pino redaction list at src/lib/logger.ts:5-14, and the pg_advisory_lock migration runner in src/migrate.ts.
  - evidence: /Users/frankbisignano/dev/elos/apps/elos-api/src/middleware/auth.ts:54; /Users/frankbisignano/dev/elos/packages/elos-shared/src/index.ts:1-26; `ls apps/elos-api/migrations/*.sql | wc -l` → 38; `wc -l apps/elos-api/migrations/*.sql | tail -1` → 2192
  - implication: Copy the catalog data and ~200 lines of plumbing; write everything else. Budget the backend as a 3-4 week greenfield build, not a fork. The catalog should ship as a versioned, immutable JSON blob in the app bundle plus an ETag'd CDN copy, not as a Postgres table with a runtime query.
- **An `updated_at`-based sync cursor is provably unsound on Postgres and will silently drop rows; a per-user bigint sequence assigned under a row lock is the correct primitive.** _(high)_
  - detail: `now()`/`CURRENT_TIMESTAMP` returns the transaction *start* time, while MVCC visibility is determined by *commit* order. Transaction A starts at t=10 and commits at t=13; transaction B starts at t=11 and commits at t=12. A client pulling at t=12.5 sees only B's row and sets cursor=11. A's row carries updated_at=10 < 11 and is never delivered again. The fix: `CREATE TABLE sync_state (user_id uuid PRIMARY KEY, last_seq bigint NOT NULL DEFAULT 0);` plus `CREATE FUNCTION next_seq(p_user uuid) RETURNS bigint LANGUAGE sql AS $$ UPDATE sync_state SET last_seq = last_seq + 1 WHERE user_id = p_user RETURNING last_seq; $$;`. The UPDATE takes a row-level lock held until COMMIT, so a second writer for the same user blocks until the first commits — seq order is exactly commit order. Because it is an UPDATE rather than a sequence, an aborted transaction rolls its increment back, so the stream is gap-free as well as monotonic. Contention is per-user only; a lifter generates well under 10 writes/second.
  - evidence: PostgreSQL docs, Date/Time Functions: now() returns transaction start time — https://www.postgresql.org/docs/18/functions-datetime.html ; the missed-row class is documented in the wild at https://github.com/airbytehq/airbyte/issues/14732 ("SQL Sources should include previous sync's cursor value ... as not to skip rows added mid-sync")
  - implication: Every syncable table carries `seq bigint NOT NULL` with a `UNIQUE (user_id, seq)` index, and the pull cursor is a single opaque bigint per user. This is the one design decision that must be right before any table is created, because retrofitting it means rewriting every write path.
- **Client-generated UUIDv7 primary keys eliminate the entire serverID/localID reconciliation bug class that produced Elos's most severe data-loss defect.** _(high)_
  - detail: Elos assigns ids server-side (`id UUID PRIMARY KEY DEFAULT gen_random_uuid()`, migrations/005_create_exercise_sets.sql:2) and the client carries both a local id and a `serverID`. The retry loop filters `record.syncPending && record.serverID.isEmpty` (AppViewModel.swift:1417), so an offline edit to an already-synced split is never retried — while the down-sync overwrites it. If the client mints the id, there is no `serverID`, no empty-vs-populated branch, and no reconciliation step. Postgres 18 (released Sept 2025) ships a built-in `uuidv7()` for server-side defaults, and Swift can generate the same shape client-side; UUIDv7's time-ordered prefix keeps B-tree index locality, unlike UUIDv4. Server accepts the client id and rejects any id it has already seen bound to a different user.
  - evidence: /Users/frankbisignano/dev/elos/apps/elos-api/migrations/005_create_exercise_sets.sql:2; prior-research.md backend section (AppViewModel.swift:1417 retry filter); PostgreSQL 18 release notes E.6 — https://www.postgresql.org/docs/current/release-18.html ; https://www.dbvis.com/thetable/uuidv7-in-postgresql-18-what-you-need-to-know/
  - implication: Declare `id uuid PRIMARY KEY` with no DEFAULT on every user-owned table and require the client to supply it. The iOS model layer then has exactly one identity per record for its whole life, on-device and on-server.
- **A per-user mutation ledger keyed on a client-generated mutation_id is the exact, minimal fix for the duplicate-set defect, and it belongs in the protocol rather than as a UNIQUE constraint per table.** _(high)_
  - detail: Elos's failure: exercise_sets has no UNIQUE constraint beyond the PK (migrations/005_create_exercise_sets.sql:1-16), `postSet` sets syncPending on any error and `flushSets` re-POSTs every set where serverID is empty, so a POST that landed but whose response was lost inserts twice — inflating tonnage, hard-set counts and e1RM PRs. A per-table UNIQUE fixes only that table. The general fix is `CREATE TABLE mutation_log (user_id uuid NOT NULL, mutation_id uuid NOT NULL, applied_seq bigint NOT NULL, result jsonb NOT NULL, created_at timestamptz NOT NULL DEFAULT now(), PRIMARY KEY (user_id, mutation_id));` with an index on created_at for a 30-day prune. Every mutation in a push batch carries a `mutation_id`; the server checks the ledger inside the same transaction and returns the stored `result` on replay. Emit a `mutation_replay_total` counter — a spike is the earliest possible signal of a client retry storm.
  - evidence: /Users/frankbisignano/dev/elos/apps/elos-api/migrations/005_create_exercise_sets.sql:1-16 (no UNIQUE on session_id, exercise_name, set_index); prior-research.md backend finding on WorkoutSyncService.swift:275-290
  - implication: Retries become free and unconditional on the client, which is what makes an offline-first queue simple. Combined with client-generated UUIDv7 ids, upserts are naturally idempotent even before the ledger is consulted.
- **Storing the program as three normalized tables with fractional order keys — rather than one TEXT blob — is what makes concurrent multi-device program editing merge instead of destroy.** _(high)_
  - detail: Elos stores `user_split_days.exercises_json TEXT NOT NULL DEFAULT '[]'` (migrations/023_user_splits.sql:18) and `PUT /splits/:id` deletes every day row and reinserts (splitService.ts:133-146), so two devices editing different days of the same program produce total loss for one of them. Replace with `program` / `program_day` / `program_slot`, each row carrying `seq, rev, updated_at, deleted_at, origin_device`. Two devices editing different days now touch disjoint rows and merge with no conflict at all. Ordering uses `order_key text` (a fractional index string such as 'a0', 'a0V', 'a1') rather than `order_index INTEGER` (023:13) — two devices inserting at the same position generate different keys instead of colliding on the same integer. This also un-blinds the server: with a normalized tree the API can validate a program's shape, index it, and eventually run the 4,706-line Intelligence engine server-side, which the TEXT blob makes permanently impossible.
  - evidence: /Users/frankbisignano/dev/elos/apps/elos-api/migrations/023_user_splits.sql:10-19 (exercises_json TEXT, order_index INTEGER); prior-research.md backend finding on splitService.ts:133-146
  - implication: Program editing is the only entity where a real merge is needed, and normalizing to slot granularity reduces it to row-level LWW. Budget one migration and a fractional-index helper (~60 lines) rather than a CRDT.
- **Two of Elos's audited bugs share one root cause — sets keyed by `exercise_name TEXT` — and both vanish if sets reference an `exercise_id uuid`.** _(high)_
  - detail: Bug 1: `analyticsService.ts:22` is `LEFT JOIN exercise_definitions ed ON lower(es.exercise_name) = lower(ed.name)` with no owner predicate, so one user's custom 'Bench Press' produces a second matching row and double-counts hard_sets and tonnage in the GROUP BY at :26 — for every user. Bug 2: `migrations/005_create_exercise_sets.sql:16` indexes `(user_id, exercise_name)` on the raw column, but analyticsService.ts:40 and :92 and leaderboardService.ts:163 all filter `lower(exercise_name) = lower($2)`, which that B-tree cannot satisfy. A `exercise_id uuid NOT NULL` column referencing either the shipped catalog or a `user_exercise` row makes the join owner-safe by construction and makes the index a plain equality lookup. Keep a denormalized `exercise_name_snapshot text` for display only, never for joining.

- **Per-entity conflict rules must be specified as a table in the contract, because the correct rule differs by entity and Elos's uniform last-writer-wins is what destroys program edits.** _(high)_
  - detail: Proposed rules. `workout` and `exercise_set` — a logged set is an observation, never a negotiation: accept unconditionally, order by server-stamped `updated_at` with `origin_device` as lexical tiebreak, and let a delete tombstone always beat a concurrent update (silently resurrecting a set the user deleted is worse than losing an edit). `base_rev` mismatches are accepted and merely reported. `program`/`program_day`/`program_slot` — `base_rev` is required; on mismatch reject that mutation, return the server row, and let the client re-apply onto it; because the tree is normalized to slot granularity, real conflicts are rare and no three-way merge is needed. `user_setting` — per-key rows give per-field LWW for free and structurally prevent the null-clobbering PATCH that Elos's flat `upsertProfileSchema` allows. `user_exercise` — LWW, soft delete only; the server refuses hard delete while sets reference it. `subscription`/`entitlement` — server-authoritative, pull-only, client writes rejected. Critically, LWW must order on the *server's* `now()` at apply time, not on a client timestamp, because device clocks are not trustworthy; return `server_time` on every pull so the client can compute its skew and refuse to push when |skew| exceeds 5 minutes.
  - evidence: prior-research.md backend finding on splitService.ts:133-146 (delete-all-days-and-reinsert = pure LWW) and on the flat upsertProfileSchema at schemas.ts:107-124 allowing a PATCH to null another surface's fields
  - implication: Write this table into the OpenAPI description before implementing any endpoint. The rules are cheap when designed up front and near-impossible to change once users have data on two devices.
- **Concrete endpoint contracts: two sync endpoints, one auth endpoint, one webhook, two lifecycle endpoints — nine routes total at launch.** _(high)_
  - detail: `GET /v1/sync/pull?cursor=<bigint>&limit=<=2000&types=<csv>` → `200 {changes: {workouts: Row[], sets: Row[], programs: Row[], program_days: Row[], program_slots: Row[], settings: Row[], user_exercises: Row[], entitlements: Row[]}, cursor: bigint, has_more: bool, server_time: rfc3339}`; `cursor=0` is a full bootstrap; soft-deleted rows are included with `deleted_at` set. `POST /v1/sync/push` with header `Idempotency-Key: <uuid>` and body `{device_id: uuid, mutations: [{mutation_id: uuid, entity: string, op: "upsert"|"delete", id: uuid, base_rev: int|null, fields: object}]}` → `200 {applied: [{mutation_id, id, rev, seq}], rejected: [{mutation_id, id, reason: "conflict"|"invalid"|"forbidden", server: Row|null}], cursor: bigint}`; the whole batch is one transaction opened with `SELECT ... FROM sync_state WHERE user_id=$1 FOR UPDATE`, capped at 500 mutations / 1 MB, and conflicts are reported per-mutation so a batch is never all-or-nothing (contrast Elos's 32kb `express.json` limit at index.ts:49, which a legal 7-day split can exceed and which surfaces as a 500). Plus `POST /v1/auth/apple`, `POST /v1/auth/refresh`, `POST /v1/entitlements/link`, `POST /v1/webhooks/revenuecat`, `POST /v1/export`, `DELETE /v1/account`, `GET /healthz`, `GET /readyz`, `GET /v1/catalog/latest`.
  - evidence: /Users/frankbisignano/dev/elos/apps/elos-api/src/index.ts:49 (32kb limit) and :79-92 (14 unversioned route mounts)
  - implication: Nine routes is the entire launch surface — versus 14 route mounts and dozens of endpoints in Elos. A small surface is what makes a Testcontainers+supertest suite with full route coverage achievable for one person.

### Risks
- The per-user next_seq row lock serializes every write transaction for one user. This is correct and cheap for a lifting app, but any future feature that fans out writes across many users in one transaction (a leaderboard recompute, a bulk migration, a community-program import that touches subscribers) will deadlock or serialize badly. Enforce a rule that a transaction may lock at most one sync_state row, and give background jobs a separate write path that does not allocate seq.
- The PowerSync-versus-custom decision is owned jointly by this stream and the client persistence stream, and neither can decide alone. If the client picks SwiftData, PowerSync is impossible; if the client picks GRDB/SQLite, PowerSync may make this entire document unnecessary. Sequence that decision before either stream writes code, or one of them will be thrown away.
- The 1k/10k/100k cost figures combine verified vendor unit prices with my own traffic and storage model (87 sync calls/user/month, ~150 bytes/set row). The unit prices are sourced; the request and storage volumes are estimates and have not been measured against any real client. A 3x error in sync frequency changes the 100k-user figure materially.
- PowerSync's per-GB overage rate above the Pro plan's 2GB/month allowance was not verified, so its 10k-user cost is genuinely unknown and could plausibly be anywhere between $49/mo and the $599/mo Team tier.
- Sign in with Apple only forecloses Android and complicates any future web client (which needs a Services ID and the JS flow). It also means a user who abandons their Apple ID has no recovery path. This is the right trade for an iOS-only launch and a real constraint on any 2027 platform expansion.
- Client-first entitlement granting means a jailbroken or receipt-spoofed device can grant itself Pro locally. For a $12/mo lifting app this is an acceptable loss, but it must be a conscious decision — the server can only detect the mismatch (entitlement_mismatch_total), not prevent it, without breaking Family Sharing.
- Server-stamped LWW ordering means an offline device pushing a two-week-old edit beats a fresher edit from a device that synced yesterday. The server_time skew check mitigates clock lies but not genuine long-offline pushes. Consider carrying client_updated_at as a secondary tiebreak for program entities specifically, and accept the residual case for logged sets where it barely matters.
- Every design in this document assumes the science engine eventually wants server-visible structured data (normalized programs, exercise_id joins). If the product decision is that all intelligence stays permanently on-device, then CloudKit + CKSyncEngine becomes substantially more attractive than it appears here and this whole backend shrinks to entitlements plus community content.
- Migrating catalog data out of the 38 existing migrations into a build-time artifact requires reading and validating ~1,400 lines of seed SQL, including the muscle-attribution corrections in 040. A transcription error there silently corrupts the muscle-attribution layer the credibility audit identified as the app's most defensible asset — treat the extraction as a data migration with golden tests, not a copy-paste.

### Open questions
- Does the client persistence stream choose SwiftData or SQLite/GRDB? PowerSync requires the latter, and that single answer determines whether the custom sync protocol in this document is needed at all.
- Is a web client or Android ever in scope? If yes within 18 months, Sign in with Apple only becomes the wrong choice and Supabase Auth (or adding Google with SIWA alongside for 4.8 compliance) is worth the extra dependency now rather than later.
- Should community/published programs exist at launch? They are the only feature requiring shared, cross-user data, and they bring moderation, reporting, abuse rate limits, and a takedown obligation — roughly doubling the launch backend surface beyond the nine routes specified here.
- Which do you want the server to eventually own: nothing (pure sync+entitlement), or the science engine? If the latter, the normalized program tree and exercise_id joins are mandatory and a TypeScript port of the Intelligence engine with a golden-test corpus against the Swift original needs to be scheduled.
- Is a lifetime purchase tier in the pricing plan? It changes the entitlement model (non-consumable alongside auto-renewables), forces a custom SwiftUI paywall since SubscriptionStoreView cannot mix them, and strengthens the case for RevenueCat's paywall tooling.
- What is the acceptable worst-case data-loss window? That determines whether daily backups suffice (free on Render/Neon paid tiers) or PITR is required at launch ($100/mo on Supabase, included on Neon), and it should be a stated product promise rather than an inferred one.
- Do you want one Postgres shared with Elos or a separate database? Separate is strongly recommended here, but it means a user with both apps has two identities and no shared history — a product decision, not an engineering one.
- How much of the first four weeks are you willing to spend on backend before the client work starts? The nine-route TestFlight backend is roughly two weeks of solo work including the test harness; anything less means shipping without the Testcontainers harness, which is the specific corner Elos cut.

## Local persistence + offline-first sync stack for a new iOS 26 science-based lifting app (2026)

**Summary.** Recommendation: GRDB 7 + Point-Free's SQLiteData as the local store, CloudKit private database via CKSyncEngine as the only sync transport, and no backend at all for user data in v1. Runner-up: GRDB + a hand-rolled delta protocol against your own Postgres. Reject SwiftData, PowerSync, ElectricSQL, Turso and Zero for this specific product.

The decisive facts. (1) CKSyncEngine is `@available(macOS 14.0, macCatalyst 17.0, iOS 17.0, tvOS 17.0, watchOS 10.0, *)` — verified in the local iOS 26.4 SDK — so a *standalone* Watch app (the single most-requested missing feature across MacroFactor Workouts, Alpha Progression and RP simultaneously) syncs directly, with no WatchConnectivity bridge and no server. (2) CloudKit's private database is billed against the user's iCloud quota, not yours: $0/mo forever at any user count, which matches a niche whose realistic ceiling is $300–800k ARR and whose loudest objection is "leasing my own training history." (3) SwiftData gives you no control over SQLite durability pragmas — `ModelConfiguration.init` exposes only name/schema/url/allowsSave/groupContainer/cloudKitDatabase — whereas GRDB's `Configuration.prepareDatabase` lets you set `synchronous = FULL`, which is the difference between "a committed set survives an OS panic" and "it might not."

The honest caveat: SQLiteData's CloudKit layer is young and its "field-wise last edit wins" merge has verified, documented violations (client edits beating newer server edits; local values discarded wholesale in reconciliation-on-fetch; non-deterministic ties). This is survivable *only* because you design the conflict surface away rather than trusting the merge. Sets are created on exactly one device and never concurrently edited — no conflict. Profile prefs are scalars — LWW is correct. The one genuinely mutable document, the program/split, gets modelled as an **immutable version chain plus a one-column pointer**, so the merge engine is never asked to merge a document; the worst case is that the other device's version wins the pointer while yours remains intact and restorable.

Everything else follows: soft-delete only (CloudKit deletions are unconditional and cannot lose a race), sync facts and derive analytics, keep the 1,697-record equipment catalog out of CloudKit entirely, and make every set write a checked `try db.write` — the exact opposite of Elos, where 87 unchecked `try? save()` calls include the sole durability point for a logged set.

### Findings
- **CKSyncEngine is available on watchOS 10.0+, so a standalone Apple Watch app can sync via CloudKit with no phone bridge and no server.** _(high)_
  - detail: Read directly from the installed SDK, not from docs. In /Applications/Xcode.app/Contents/Developer/Platforms/WatchOS.platform/Developer/SDKs/WatchOS.sdk/System/Library/Frameworks/CloudKit.framework/Modules/CloudKit.swiftmodule/arm64e-apple-watchos.swiftinterface line 1175-1176: `@available(macOS 14.0, macCatalyst 17.0, iOS 17.0, tvOS 17.0, watchOS 10.0, *)` immediately preceding `final public class CKSyncEngine : Swift.Sendable`. The identical availability line appears at 1213-1214 of the arm64e-apple-ios.swiftinterface in iPhoneOS26.4.sdk. This matters more than any other single fact here: the prior competitive research established that a missing Watch app is the top complaint at MacroFactor Workouts, Alpha Progression AND RP Hypertrophy simultaneously, and the usual objection to a standalone Watch app is that you have to build a second sync path for it. With CKSyncEngine you do not — the watch runs the same store and the same engine against the same private CloudKit container.
  - evidence: /Applications/Xcode.app/Contents/Developer/Platforms/WatchOS.platform/Developer/SDKs/WatchOS.sdk/System/Library/Frameworks/CloudKit.framework/Modules/CloudKit.swiftmodule/arm64e-apple-watchos.swiftinterface:1175-1176
  - implication: Watch is no longer a phase-2 architectural problem. Design the schema and sync layer once, target iOS 26 + watchOS 26, and the Watch app is a UI project rather than a sync project. Conversely, any stack that cannot run on watchOS (a hand-rolled HTTP protocol needs auth token handling, background refresh and retry on the watch too) silently makes the Watch app 3x more expensive.
- **SwiftData exposes no way to control SQLite durability pragmas; GRDB does, and the difference is decisive for a set logger.** _(high)_
  - detail: `ModelConfiguration` in the iOS 26.4 SDK has exactly two initializers (swiftinterface lines 47-48) and neither accepts journal-mode, synchronous, busy-timeout, or any pragma hook — the only knobs are name, schema, url, isStoredInMemoryOnly, allowsSave, groupContainer and cloudKitDatabase. GRDB by contrast exposes `Configuration.prepareDatabase(_:)` (GRDB/Core/Configuration.swift:241), inside which you run `PRAGMA synchronous = FULL`, plus `Configuration.journalMode` (Configuration.swift:322). The durability difference is real and documented by SQLite's own maintainers: in WAL mode with synchronous=NORMAL, a committed transaction reaches the filesystem but fsync() is not called, so "that record might not have made it to stable storage" and can roll back on power loss or kernel panic — while an *application* crash never loses it, because the data is already in the OS. For a set logger the cost of FULL is one fsync per commit, and a commit happens roughly once every 45-120 seconds while a human rests between sets. It is free in this domain.
  - evidence: /Applications/Xcode.app/Contents/Developer/Platforms/iPhoneOS.platform/Developer/SDKs/iPhoneOS.sdk/System/Library/Frameworks/SwiftData.framework/Modules/SwiftData.swiftmodule/arm64e-apple-ios.swiftinterface:47-48 ; https://raw.githubusercontent.com/groue/GRDB.swift/master/GRDB/Core/Configuration.swift:241,322 ; https://sqlite.org/forum/info/9d6f13e346231916
  - implication: Adopt GRDB and set `journalMode = .wal` plus `PRAGMA synchronous = FULL` in `prepareDatabase`. This buys the literal product promise ('never loses a workout') at zero measurable cost, and it is a promise SwiftData structurally cannot make because it does not let you ask for it.
- **SwiftData change history is iOS 18+, but the push-based HistoryObserver is iOS 27 and does not exist in the iOS 26.4 SDK — so on an iOS 26 target you would have to poll fetchHistory yourself.** _(high)_
  - detail: Grepping the iOS 26.4 SwiftData swiftinterface for `HistoryObserver` returns nothing. What does exist: `HistoryDescriptor` at line 605 guarded by `@available(macOS 15, iOS 18, tvOS 18, watchOS 11, visionOS 2, *)` (lines 603-605), `fetchHistory`/`deleteHistory` at 441/444 under the same availability, `HistoryTransaction` (525), `DefaultHistoryDelete` carrying a `HistoryTombstone` (interface offset 149-155 within the history block), and `Schema.Attribute.Option.preserveValueOnDeletion` (line 916). A July 2026 write-up of HistoryObserver states plainly: "Starting with iOS 27, SwiftData introduces HistoryObserver", and also that "HistoryObserver supports one way synchronization... changes made on the server are not automatically synchronized back to the client", and that tracking deletions requires an `isDeleted` soft-delete flag anyway.
  - evidence: /Applications/Xcode.app/Contents/Developer/Platforms/iPhoneOS.platform/Developer/SDKs/iPhoneOS.sdk/System/Library/Frameworks/SwiftData.framework/Modules/SwiftData.swiftmodule/arm64e-apple-ios.swiftinterface:441,444,525,603-605,916 (grep for HistoryObserver returns no matches) ; https://azamsharp.com/2026/07/16/syncing-swiftdata-with-a-custom-backend-using-historyobserver.html
  - implication: The 'SwiftData now has history tracking so custom sync is easy' argument does not apply to an iOS 26 deployment target in Aug 2026. You would inherit a polling loop, your own token persistence, your own tombstone design, and still have to build the entire down-sync half by hand. That is the same amount of work as a custom protocol, minus the control.
- **Point-Free's SQLiteData is a live, actively-released GRDB-based SwiftData replacement with built-in CloudKit sync, and its SyncEngine floor (iOS 17 / watchOS 10) is far below the iOS 26 target.** _(high)_
  - detail: SQLiteData is the 1.0 rename of SharingGRDB. Releases as of this research: 1.10.0 (2026-08-11), 1.9.0 (2026-08-03), 1.8.2 (2026-07-29), 1.8.1 (2026-07-28), 1.8.0 (2026-07-27) — all non-prerelease, i.e. a shipping release roughly weekly. Package.swift declares swift-tools-version 6.1 and platforms .iOS(.v16)/.macOS(.v13)/.tvOS(.v16)/.watchOS(.v9). The sync type is `public final class SyncEngine: Observable, Sendable` in Sources/SQLiteData/CloudKit/SyncEngine.swift:26, guarded by `@available(iOS 17, macOS 14, tvOS 17, watchOS 10, *)` at line 25 — it wraps CKSyncEngine. Usage is a single declaration at app start: `$0.defaultSyncEngine = SyncEngine(for: $0.defaultDatabase, tables: Item.self)`, and tables are opt-in — "You must explicitly provide all tables that you want to synchronize" (CloudKitSync.md:93). The ergonomics replacement for @Query is the `@FetchAll`/`@FetchOne` property-wrapper family plus the `@Table` macro over GRDB.
  - evidence: https://api.github.com/repos/pointfreeco/sqlite-data/releases ; https://raw.githubusercontent.com/pointfreeco/sqlite-data/main/Package.swift:1-13 ; https://raw.githubusercontent.com/pointfreeco/sqlite-data/main/Sources/SQLiteData/CloudKit/SyncEngine.swift:25-26 ; https://raw.githubusercontent.com/pointfreeco/sqlite-data/main/Sources/SQLiteData/Documentation.docc/Articles/CloudKitSync.md:93
  - implication: This is the option that removes the false tradeoff in the brief's question 2. You do not have to give up @Query ergonomics to get GRDB — @FetchAll is the direct equivalent, backed by GRDB's ValueObservation, and CloudKit sync comes with it. It also means the 'give up @Query' cost in the GRDB column of every comparison article is out of date.
- **SQLiteData's conflict resolution is 'field-wise last edit wins', is not customizable, and an independent audit documents concrete cases where it violates its own stated rule and silently discards local data.** _(high)_
  - detail: The official position (CloudKitSync.md:461-472): "Conflicts are handled automatically using a 'last edit wins' strategy for each column", "currently not customizable", "We do not employ more advanced merge conflict strategies, such as CRDT." Mechanically, per-field timestamps are stored on the CKRecord via `encryptedValues[at:]` under keys like `sqlitedata_icloud_userModificationTime_title`, alongside a `SyncMetadata` table holding `lastKnownServerRecord`, `_lastKnownServerRecordAllFields` and `userModificationTime`. The independent audit (structuredpath/sqlite-data-sync-notes, written against 1.4, updated for 1.8.1) documents three real defects: (a) merge-conflict-on-fetch — "When the client and the server edit the same field concurrently, the pending client edit always wins, even when the server's edit has a newer timestamp" because `isRowValueModified` "never consults per-field timestamps" (tracked as issue #354); (b) reconciliation-conflict-on-fetch — with no last-known server record, "the reconciliation step is skipped entirely" and "all writable columns are written to the local database row, wholesale overwriting the locally created values pending upload... even when they are newer"; (c) equal timestamps resolve non-deterministically because the comparison uses `<=`. It also warns that the test suite "does not reflect the production outcome" for several of these paths. Maintainer position (Stephen Celis, discussion #272): "We just felt that per-field last-wins works for 99% of the use cases out there" and "We are definitely open to configurable conflict resolution"; as of Aug 2026 the work moved to a separate repo with no committed timeline.
  - evidence: https://raw.githubusercontent.com/structuredpath/sqlite-data-sync-notes/main/CurrentBehavior.md (sections 2.3-2.6 and their WARNING callouts) ; https://raw.githubusercontent.com/pointfreeco/sqlite-data/main/Sources/SQLiteData/Documentation.docc/Articles/CloudKitSync.md:461-472 ; https://github.com/pointfreeco/sqlite-data/discussions/272 ; https://github.com/pointfreeco/sqlite-data/issues/354
  - implication: Do not treat SQLiteData's merge as a safety net. Adopt it only with a schema whose conflict surface is deliberately near-zero (see the per-entity model below), and write your own conformance tests rather than trusting the library's — the audit explicitly says library tests and production diverge. Case (b) is the dangerous one for this domain: it fires when sync metadata is lost but user data is kept, e.g. after signing out of and back into iCloud.
- **CloudKit-synced schemas carry hard, permanent constraints: UUID primary keys on every table, no UNIQUE constraints, restricted ON DELETE actions, and three forbidden migrations.** _(high)_
  - detail: From CloudKitSync.md, all verified in the source doc: primary keys "must be globally unique identifiers, such as UUID, and cannot be an autoincrementing integer", declared as `"id" TEXT PRIMARY KEY NOT NULL ON CONFLICT REPLACE DEFAULT (uuid())` with the ON CONFLICT clause placed "directly after NOT NULL" (:133-154). Every synchronized table "must have a single primary key and cannot have compound primary keys. This includes join tables" (:203-204). "uniqueness constraints are not allowed in schemas, and this will be validated when a SyncEngine is first created" (:255-266). "Currently the only actions supported for ON DELETE are CASCADE, SET NULL and SET DEFAULT. In particular, RESTRICT and NO ACTION are not supported" (:249). ### Recommendations
- [weeks] **Adopt GRDB 7.11+ as the local store, Point-Free SQLiteData 1.10+ for @Table/@FetchAll ergonomics and its CKSyncEngine-backed SyncEngine, and CloudKit's private database as the only sync transport. Ship v1 with no backend for user data at all.** — It is the only option that simultaneously satisfies all four weighted constraints: solo dev (zero ops, zero server cost, no auth system to build), offline-first as a hard requirement (writes always land locally first, sync is a background mirror), never losing a set (GRDB gives you synchronous=FULL and checked writes; CloudKit gives idempotent upserts keyed on your own UUID), and a Watch app (CKSyncEngine is watchOS 10+, verified in the SDK). It also delivers the 'your training history lives in your iCloud, not on my server' story that the prior GTM research identified as this niche's loudest objection. The known weakness — SQLiteData's merge engine — is neutralized by schema design rather than trusted.
- [hours] **Configure the database for durability explicitly in migration zero: journalMode = .wal, and `PRAGMA synchronous = FULL` inside Configuration.prepareDatabase. Then ban `try?` on every write path.** — With synchronous=NORMAL a committed transaction survives an app crash but can roll back on an OS panic or power loss. FULL costs one fsync per commit; in this app a commit happens once per logged set, roughly every 45-120 seconds. The cost is unmeasurable and it converts the marketing claim into a technical guarantee. The `try?` ban is the direct lesson from the existing app, where the sole durability point for a logged set (TrainViewModel.swift:102) discards its own error and 87 unchecked saves outnumber checked ones 87:1.
- [days] **Model programs/splits as an immutable version chain: `program(id, currentVersionID, name, deletedAt)` pointing at `programVersion(id, programID, createdAt, ...)` with immutable `programDay` and `programDayExercise` children. Editing a program inserts a new version and updates one column.** — This is the single highest-leverage design decision in the whole plan. It removes the only entity in the domain with a real multi-field concurrent-edit surface, which is exactly the entity the current app already loses data on and exactly where SQLiteData's documented merge violations would land. Under this shape the merge engine only ever arbitrates a single scalar pointer; the losing device's edit is not destroyed, it is an unreferenced version that the UI can offer to restore ('this program was also edited on your iPhone — view that version'). It also gives you program history for free, which is a genuine feature for a periodization-aware app.
- [hours] **Use soft deletes universally — every synced table carries `deletedAt INTEGER` — and never issue a hard DELETE on a row that has ever been synced. Physically purge only rows where deletedAt is older than 90 days AND SyncMetadata confirms an acknowledged server record.** — CKSyncEngine treats deletions as trusted and unconditional with no conflict check, which makes hard delete the one operation in this stack that can destroy data with no recourse and no error. Soft delete also makes deletion a normal field-wise LWW update that participates in the same merge as everything else, and it gives you a trivially cheap undo for the accidental 'deleted my whole program' support ticket. The purge condition must include sync confirmation, or you will purge a tombstone before a rarely-used second device ever learns about it.
- [hours] **Sync facts only; derive everything else locally. Sync: workoutSet, workoutSession, program/programVersion/programDay/programDayExercise, userExercise, gym, gymEquipment, profilePrefs. Do NOT sync: personal records, weekly volume aggregates, muscle-coverage scores, e1RM curves, readiness scores, or any engine output.** — Derived data cannot conflict if it is never transmitted, and it is reconstructible from the facts by definition. Syncing it multiplies the record count, multiplies the conflict surface, and creates the worst class of bug — two devices disagreeing about a number the user can see. The science engine is already pure Foundation value types (44 files, 4,706 lines, zero framework imports), so recomputation is cheap and deterministic. Keep a local materialized cache table if recompute cost ever becomes visible, but mark it non-synced and rebuild it on schema version change.
- [days] **Ship the exercise definitions and the ~1,697-record equipment catalog as a read-only SQLite file in the app bundle, attached as a second database, versioned by app release — never as synced user rows.** — Reference data is not user data. Putting it in CloudKit would mean thousands of CKRecords per user for content that is byte-identical for everyone, on the user's iCloud quota, with a conflict surface for data nobody edits. A bundled read-only database is faster, free, offline by construction, and updated atomically by an App Store release. User customizations live in a separate small `userExercise` table that IS synced, and user-added machines in `gymEquipment`.
- [hours] **Generate RFC 9562 UUIDv7 client-side and store every primary key as lowercase TEXT, registering the generator as the SQLite `uuid()` function used in `"id" TEXT PRIMARY KEY NOT NULL ON CONFLICT REPLACE DEFAULT (uuid())`.** — CloudKit forbids autoincrement integer keys and encodes the primary key into the CKRecord recordName (must be under 255 chars, must not start with an underscore), so TEXT UUID is mandatory. Between v4 and v7 there is no meaningful SQLite performance difference at this scale (510.70 vs 500.03 Kelem/s insert at 200k rows), so choose v7 for its real benefits: time-ordered so B-tree inserts append instead of scatter, `ORDER BY id` is chronological, and a raw id in a crash report tells you when the row was created. Foundation's UUID is v4 only, so this is ~30 lines you own rather than a dependency.
- [days] **Write a sync conformance test suite before writing sync-dependent features: drive two in-memory SQLiteData stores against a mock CloudKit container and assert the outcome of each of the six documented scenarios (send, fetch, merge-conflict-on-send, merge-conflict-on-fetch, reconciliation-on-send, reconciliation-on-fetch).** — The independent audit explicitly warns that SQLiteData's own test suite diverges from production behavior in several of these paths — the mock server does not populate modificationDate, and in at least two scenarios the test outcome is the opposite of the production outcome. You therefore cannot rely on the library's green tests as evidence that your data survives. Owning these six assertions also means that when you upgrade SQLiteData, you find out immediately whether the merge semantics changed under you.
- [hours] **Pin SQLiteData to an exact version, upgrade deliberately, and keep the escape hatch documented: the SyncEngine writes to ordinary GRDB tables and keeps its state in a separate metadatabase, so removing it leaves the application database fully intact.** — This is what makes the recommendation risk-acceptable rather than a bet. The dependency risk is concentrated in one replaceable component, not in the data model. If the CloudKit layer proves unreliable in the field, you keep the identical schema and point PowerSync or a hand-rolled protocol at the same tables. Weekly releases (five in the last three weeks) are a sign of health but also a reason not to float the version on a data-critical dependency.
- [days] **Build an in-app Sync Diagnostics screen in v1: last successful fetch, last successful send, pending record count, last error with its CKError code, iCloud account status, and a 'copy diagnostics' button.** — The documented reason teams left CloudKit in 2026 is not data loss, it is blindness — 'When a user's data won't sync, we have no view into what happened on Apple's side.' You get no server logs, ever. A diagnostics screen is the cheapest possible substitute and it converts an unanswerable support ticket into a paste. Explicitly detect and surface the account-unavailable and iCloud-terms-not-accepted states, because the latter is the documented silent-failure mode that stopped Watch sync for a real shipping app.
- [hours] **Adopt an additive-only migration policy from day one, enforced by a checklist and a test: never remove a column, never rename a column, never rename a table. New non-null columns must be declared `NOT NULL ON CONFLICT REPLACE DEFAULT <value>`.** — These are not stylistic preferences, they are hard requirements of a distributed schema — old app versions on a second device must still be able to insert rows that new versions can read. SQLiteData validates some of this at SyncEngine construction, but not migration history. Getting this wrong is not a crash, it is a device that silently stops accepting records from its sibling. Note this constraint would apply identically under SwiftData+CloudKit, so it is not a cost of the recommended stack.
- [hours] **On store-open failure, preserve and rename rather than delete: move the file to `store-corrupt-<ISO8601>.sqlite`, open a fresh store, and present an explicit recovery screen offering export of the preserved file.** — The existing app's recovery path deletes the store on the first init failure (ElosApp.swift:74) and then tells the user 'Your data is safe' — which is false. In a product whose core promise is not losing data, the failure mode must be loud and recoverable. Renaming costs one line and turns an unrecoverable wipe into a support-recoverable incident.
- [days] **Ship export before you ship sync: one-tap JSON and CSV export of every set, session and program, plus a nightly automatic local snapshot of the database file retained for 7 days.** — Export is simultaneously the ultimate data-loss backstop, an explicit competitive checkbox (data export is on MacroFactor Workouts' feature list and 'no export' is a named complaint elsewhere), and the thing that makes the lifetime tier credible. With GRDB it is a SQL query and a file write. The nightly snapshot is a `VACUUM INTO` to a dated file — cheap, atomic, and it means a catastrophic sync bug costs the user at most one day.
- [weeks] **Build the Watch app as a standalone target with its own GRDB store and its own SyncEngine on the same CloudKit container. Do not use WatchConnectivity as the sync transport.** — CKSyncEngine is available on watchOS 10+, so the watch is a first-class peer rather than a mirror, and phone-in-locker logging works. WatchConnectivity as a transport would mean a second, hand-written, bespoke sync protocol with its own conflict semantics — the exact thing this whole plan exists to avoid. Note the caveat: PowerSync's multi-process/app-group support is experimental, which is another reason the CloudKit path is the better fit for a two-target design.
- [weeks] **Defer any Postgres backend until a feature genuinely requires it, and when it arrives make it content-only: a read-only program/creator catalog with no authority over user data.** — The prior GTM research concluded that at a realistic $300-800k ARR ceiling 'the correct amount of backend investment is small and boring'. A content API needs no user accounts, no sync protocol, no conflict resolution, no GDPR data-controller burden for training data, and can be a static JSON bundle behind a CDN before it is ever a server. Keeping user data exclusively in CloudKit and content exclusively in the API means the two systems never need to agree about anything.
- [hours] **Store every enum-shaped column as TEXT rawValue, never as an integer, and treat unknown values as a preserved passthrough rather than a decode failure.** — A device running v1.0 will receive records written by a device running v1.4. If splitType or progressionScheme is an Int rawValue with no case for the new value, the older device either crashes or drops the row. Strings at least round-trip legibly and can be preserved. This is a documented CloudKit production trap and it costs nothing to get right on day one, while being effectively unfixable later.
- [hours] **Acquire two physical devices for the sync development loop (iPhone plus Apple Watch or a second iPhone) and treat simulator results for anything sync-related as meaningless.** — Simulators do not receive push notifications, so CloudKit changes never arrive — SQLiteData's own docs and the CKSyncEngine production write-up both say so explicitly. This project's own memory already records that the simulator is unreliable for verification here and that sandboxed xcodebuild cannot run tests. Discovering this after the sync layer is written is the expensive ordering.
- [hours] **Do not enable SQLiteData's CloudKit record sharing (multi-user collaboration) in v1.** — Sharing adds the shared database, participant management, share acceptance UI, and a second SyncEngine instance — and the library's own documentation notes it 'brings extra complications... beyond the existing complications of sharing a schema'. The v1 product is a single-user training log. Coach/client sharing is a plausible v2 differentiator but it should be scoped as its own project against a proven sync foundation, not carried as risk through launch.

### Risks
- SQLiteData's CloudKit layer is young and has verified merge defects. An independent audit against v1.8.1 documents that in merge-conflict-on-fetch the pending client edit always wins even when the server edit is newer (issue #354), that reconciliation-on-fetch skips resolution entirely and wholesale overwrites locally created values, and that equal timestamps resolve non-deterministically. The mitigation (immutable program versions, single-device set creation, soft deletes) shrinks the blast radius to near zero for this domain but does not eliminate the dependency risk.
- The reconciliation-conflict path — the worst one, where local values are discarded without consulting timestamps — is triggered by loss of sync metadata while user data is retained, which is exactly what happens when a user signs out of and back into iCloud. That is a normal user action, not an edge case, and it needs an explicit test and probably an explicit guard.
- You will have zero server-side observability, permanently. When a user reports 'my Tuesday workout is missing', there are no logs to check. This is the documented reason real teams left CloudKit in 2026. The diagnostics screen mitigates but does not solve it, and it will cost real support hours.
- CloudKit sync is invisible in the simulator and requires physical devices, which slows every iteration on the highest-risk subsystem. Combined with this machine's recorded inability to run tests under sandboxed xcodebuild, the verification loop for sync is materially worse than for the rest of the app.
- The CloudKit schema constraints are permanent and unforgiving: no removing columns, no renaming columns, no renaming tables, no UNIQUE constraints outside the primary key, single non-compound UUID primary key on every table including join tables. A schema mistake made in month one cannot be cleanly undone in month twelve — it can only be worked around with a dead column carried forever.
- CloudKit ties the product to the Apple ecosystem with no web client and no Android path. If the go-to-market later demands a web tool that touches user data (the prior research recommends a free web tool, though a stateless one), or coach dashboards, that is a re-architecture rather than an addition. The escape hatch is real but it is still weeks of work plus a migration of every existing user's data out of iCloud.
- Third-party dependency concentration: the sync layer is a single small-team open-source package shipping roughly weekly. A maintainer pause, a breaking rewrite, or a regression in a release you adopt lands directly on the subsystem whose failure mode is losing user training history. Pinning and a conformance suite reduce this to a manageable risk, not a zero one.
- Apple's own track record here is uneven. The prior research recorded SwiftData+CloudKit sync regressions in iOS 26.0/26.1 (duplicate records, no refresh after sync), and a shipping app reported Apple Watch silently ceasing to sync when users had not accepted new iCloud terms. Those are platform failures no amount of client-side care prevents.
- A solo developer building a set logger will be tempted to ship the logging UI first and the sync conformance tests 'later'. If sync ships without the six-scenario test suite, the first data-loss report will arrive from a paying user rather than from CI, and in this category a single credible 'it lost my workouts' review is disproportionately expensive.
- The immutable-program-version design adds real row volume and a UI surface (version history, restore, 'edited elsewhere' resolution) that a naive mutable-document design does not need. If that UI is skipped, the losing edit is technically preserved but practically invisible, which is functionally the same as losing it.
- synchronous=FULL guarantees durability of committed transactions but not of un-committed UI state. If the app is killed between the user tapping 'complete set' and the write committing, the set is gone. The write must happen synchronously on the tap, not batched or deferred to a debounced save, or the durability configuration is decorative.
- Judgment calls in this report that are not externally verified: that this domain's real concurrent-edit rate on sets is near zero (reasoned from usage patterns, not measured), and that the ~20x GRDB-over-SwiftData insert figure circulating in 2026 comparison posts is directionally right — I could not locate the primary benchmark behind that number and it should not be used to justify anything.

### Open questions
- Is a web client ever in scope for user training data? If yes at any point in the next 24 months, the answer flips to GRDB + PowerSync (or a hand-rolled protocol) against your own Postgres, and CloudKit should be rejected now rather than migrated away from later.
- Are coach/client or shared-program features part of the product thesis? CloudKit record sharing exists but is materially more complex, and SwiftData still has no shared/public database — this decision changes whether the sync foundation needs a multi-user story from the start.
- Will the app require an account and identity at all? CloudKit gives you a free, zero-friction identity (the iCloud account) with no signup screen. Any feature that needs a portable identity across platforms — creator revshare attribution, subscription entitlements outside StoreKit, community posting — reintroduces a real auth system.
- Does the product need server-side visibility into aggregate training data (for improving the science engine, for content, or for investor/partner metrics)? CloudKit private database means you can never see any of it, by design. That is a feature for user trust and a constraint on product learning.
- How much of the existing Elos Intelligence layer's data contract is being carried forward? The per-set equipment identity fields (equipmentId, equipmentDedupeKey, equipmentBrandName) and the muscleTargetsJSON blob shape the set table's column list, and column decisions are effectively permanent under CloudKit sync.
- Is Apple Watch in v1 or v2? It is the single most-requested missing feature across three competitors and CKSyncEngine makes it architecturally cheap, but it is still a second UI target. If it is v1, the schema must be finalized before the Watch UI starts.
- What is the acceptable ceiling on third-party dependency risk for the sync layer specifically? An alternative is to use GRDB plus CKSyncEngine directly, writing your own ~800-1500 line sync layer instead of adopting SQLiteData's — more work, no merge-engine surprises, full control over conflict semantics. That is a genuine fork in the road and it is a taste/risk call, not a technical one.
- Will the app ever import from Hevy / Strong / Alpha Progression? Bulk import of years of history is the one operation that stresses both SQLite insert throughput and CloudKit batch limits (1 MB per upload batch), and it may justify a dedicated import path that bypasses the normal write path.

## Science engine v2 for the new standalone science-based lifting app: a buildable spec grounded in 2025–2026 evidence

**Summary.** The single most useful result of this pass is that Pelland et al. 2025's published volume-efficiency tiers and its reported marginal slope are both reproduced by one continuous square-root curve. Fitting β to the paper's own four tier increments gives β = 1.90 percentage-points of muscle size per √(fractional weekly set); that value reproduces all four increments to within 0.5 sets and implies a marginal slope of 0.263 %/set at the study mean of 13.00 sets — inside the paper's reported 0.24 % [95 % CrI 0.15, 0.33]. So the new engine does not need a lookup table or 16 invented per-muscle bands: it needs one function, `beta * (sqrt(v2) - sqrt(v1))`, plus the published SDES of 2.05 %. Everything the product wants to say about volume — "what does one more set buy you", "how many more sets until you'd notice" — falls out of that function, cited.

Two 2026 sources post-date the prior research digest and both push in the same direction. The ACSM Position Stand (MSSE 58(4):851–872, DOI 10.1249/MSS.0000000000003897, 137 systematic reviews, >30,000 participants) recommends ≥10 sets/week for hypertrophy with no per-muscle or per-experience differentiation, and states that training to failure, set structure, and periodization did not consistently affect outcomes. Steele et al.'s multi-site RCT (SportRxiv 810, April 2026, 22 sites, 87 completers) found 9 vs 36 fractional sets/week statistically equivalent. Together they mean the honest rendering of the dose curve is a band with visible counter-evidence, not a line, and certainly not a red zone.

Three engine changes follow. First, MRV disappears as a product concept — it has never been operationalized in a trial, and the red "more than you can recover from" warning (VolumeScorer.swift:92-95) is replaced by a monotonic efficiency readout that fades to an explicitly hatched "beyond the evidence" region past 43 sets. Second, the composite score is replaced by an `Assessed<Value>` type in which unknown propagates to unknown and coverage travels with every number, killing the 78/100 "Dialed in" false positive at the type level. Third, fatigue is demoted from a 14–16 %-weight scored dimension to an unscored advisory, because its four constants are uncited and its rescale actively penalizes compound-heavy sessions.

### Findings
- **Pelland et al. 2025's published volume-efficiency tier table and its reported marginal slope are both reproduced by a single square-root curve with β = 1.90 percentage-points of muscle size per √(fractional weekly set), so the volume model can be one continuous function instead of a table of invented landmarks.** _(high)_
  - detail: The paper's best-fit model for fractional weekly volume → hypertrophy is explicitly the square root model (R²marginal = 22.3 %, R²conditional = 73.3 %), marginal slope 0.24 % [95 % CrI 0.15, 0.33] at the mean fractional volume of 13.00 ± 8.87 sets/week. Table 3 gives SDES = 2.05 % and tier increments of ~6, ~8.5, ~10.75, ~12.5 additional sets at tier starts 4, 11, 19, 30. Least-squares fitting β to those four increments under gain(v) = α + β√v yields β = 1.898 (SSE 0.57), predicting increments 5.49 / 8.33 / 10.58 / 13.00 and implied tier boundaries 4, 9.5, 17.3, 27.5, 40.0 against the paper's 4, 10, 18, 29, 42. Cross-check: β/(2√13.00) = 0.263 %/set vs the reported 0.24 % [0.15, 0.33] — inside the credible interval. The buildable API is intercept-free and therefore does not require estimating α: `expectedGainDelta(from a: Double, to b: Double) -> Double { 1.90 * (sqrt(b) - sqrt(a)) }` (units: percentage points of muscle size over a typical 8–12 week block), `setsForNextDetectableIncrement(at v: Double) -> Double { let s = sqrt(v) + 2.05/1.90; return s*s - v }`. Concrete outputs: 10→11 sets buys 0.293 pp; 25→26 buys 0.188 pp; 40→41 buys 0.149 pp.
  - evidence: Pelland JC, Remmert JF, Robinson ZP, Hinson SR, Zourdos MC, Sports Medicine 2025, DOI 10.1007/s40279-025-02344-w, PMID 41343037 — §3.6.1 ("Model comparisons revealed the square root model was the best fit… = 0.24% [95% CrI 0.15, 0.33]"), Table 3 (SDES 2.05 %; tiers 4 / 5–10 / 11–18 / 19–29 / 30–42 / 43+), §3.4 medians (volume 10.5 sets/wk; mean 13.00 ± 8.87). Verbatim text extracted from https://www.fisiologiadelejercicio.com/wp-content/uploads/2025/12/The-Resistance-Training-Dose-Response.pdf; fit computed locally (β = 1.898, SSE 0.568).
  - implication: Replace TrainingScience.baseWeeklyBand (TrainingScience.swift:142-161) and VolumeBand's mev/targetLow/targetHigh/mrv quadruple with one `VolumeDoseModel` value type carrying beta = 1.90, betaCrI = 1.08…2.38 (derived from the slope CrI at v̄ = 13), sdesHypertrophy = 2.05, sdesStrength = 3.96. The engine gains a genuinely citable marginal-value function no competitor ships, and the numbers are checkable against a published table.
- **The evidence base contains no muscle-specific volume dose-response, so the 16 per-FineMuscle bands in the current engine are invented precision and must collapse to one curve applied per muscle.** _(high)_
  - detail: Pelland's tiers are defined against "Weekly Set Volume For Measured Muscle (Fractional)" with no muscle-group stratification, and the paper states moderator analyses "should be viewed as hypothesis generating." The ACSM 2026 Position Stand likewise gives a single hypertrophy figure (≥10 sets/wk) for all major muscle groups. The current engine encodes chest mev:8/14–20/mrv:26, hamstrings 6/10–16/22, biceps 8/12–18/24 etc. — 16 distinct quadruples, 64 numbers, none traceable to a source. The app's own coaching copy asserts muscle-specific tolerance ("Quads, hamstrings and calves are large, resilient muscles that generally tolerate — and benefit from — higher volume than upper-body muscles") with no citation behind it.
  - evidence: TrainingScience.swift:142-161 (baseWeeklyBand); MuscleTaxonomy.swift:30-31 (volumeRationale for .legs); Pelland 2025 Fig. 7 axis label and §4.4 moderator caveat; ACSM Position Stand, Med Sci Sports Exerc 2026;58(4):851-872, DOI 10.1249/MSS.0000000000003897, PMID 41843416 ("Hypertrophy: ≥10 sets/wk").
  - implication: v2 keeps per-muscle *accounting* (fractional credit at FineMuscle resolution is the real asset) and drops per-muscle *targets*. One curve, applied to each muscle's fractional weekly set count. This deletes 64 unsourced constants and removes the largest surface area for a knowledgeable reviewer's critique.
- **The experience multiplier (beginner 0.75 / intermediate 1.0 / advanced 1.15) has no support and should be replaced by an explicit user-declared time budget.** _(medium)_
  - detail: Pelland's models adjusted for training status as a fixed effect and the discussion states the marginal slope "was not often influenced by other variables," with all moderator analyses flagged as indirect and hypothesis-generating. ACSM 2026 gives one volume figure for healthy adults. Meanwhile the multiplier is load-bearing in the current engine: it scales every band (TrainingScience.swift:198) and therefore every tip threshold, and experience is a single self-declared enum with no calibration. Replacing it with sessions-per-week × minutes-per-session — which the app can actually observe — converts an unsupported physiological claim into an honest scheduling constraint.
  - evidence: TrainingScience.swift:164-170 and :198; Pelland 2025 §4.4 ("Moderator analyses indicated that the marginal slope… was not often influenced by other variables. However, extreme caution is warranted regarding all moderator analyses"); ACSM 2026 DOI 10.1249/MSS.0000000000003897.
  - implication: Delete `experienceScale` and `weeklyVolume(for:)` (TrainingScience.swift:41-54, :164-170). Personalization moves to: available days, minutes per session, muscles the user has opted out of, and per-exercise history. Nothing is framed as 'your body needs more'.
- **Per-muscle MRV must not exist in the product at all; the replacement for the red 'over MRV' warning is a monotonic efficiency readout that never turns red plus an explicitly hatched 'beyond the evidence' region past 43 fractional sets.** _(high)_
  - detail: Pelland 2025 states the tiers "indicate no clear plateau in the primary meta-regression" and that "caution is warranted as few studies have explored ~25+ fractional weekly sets"; the 43+ tier is labelled "Insufficient data to inform efficiency or potentially less hypertrophy." No trial has ever operationalized MRV. The current engine turns this into a hard red state: VolumeStatus.excessive fires at sets > band.mrv and emits "may be more than you can recover from (~26 is plenty). Trim a set or two." Concretely: a lifter doing 27 fractional chest sets/week is told to cut, when the actual evidence says that lifter is in the 'lower efficiency' tier and each further set still buys ~0.18 pp. Proposed replacement enum: `EfficiencyTier { belowMinimum(<4), higher(4..<11), intermediate(11..<19), lower(19..<30), lowest(30..<43), beyondEvidence(43+) }` with only `belowMinimum` styled as an actionable warning; the high end is rendered as diminishing return per set plus a time cost in minutes, never a health/recovery claim.
  - evidence: VolumeScorer.swift:90-95 (vol-high tip text); MuscleVolumeAnalyzer.swift:325 (`if sets > band.mrv { return .excessive }`); TrainingScience.swift:106 (`let mrv: Double // maximum recoverable volume`); Pelland 2025 §4.2 and Table 3 verbatim.
  - implication: Delete `VolumeBand.mrv`, `VolumeStatus.excessive`, and the vol-high tip. The high-volume conversation becomes budgetary ('these 10 extra sets cost you ~25 minutes a week and buy ~0.17 pp') rather than physiological. This is also the single clearest differentiator against RP-style apps, which sell the MRV concept.
- **A multi-site RCT published in April 2026 found 9 vs 36 fractional weekly sets statistically equivalent for arm and thigh muscle CSA, which post-dates the prior research digest and forces the dose curve to be rendered as a band with visible counter-evidence rather than a line.** _(medium)_
  - detail: Steele J, Gschneidner D, Carlson L, Fisher J, "A test of higher and lower fractional volumes of resistance training upon arm and thigh muscle area: A multi-site randomised trial", SportRxiv preprint 810, posted 8 April 2026 (v3 23 April 2026). 22 sites, 125 recruited / 120 randomised (low volume n = 56 at 9 fractional sets/wk, high volume n = 64 at 36 fractional sets/wk), 12 weeks, 87 completed post-testing. Result: statistical equivalence, effect estimate 0.023 [90 % CI −0.044, 0.091], p = 0.032 for equivalence; time effect 0.087 [95 % CI 0.047, 0.128]. Caveats that matter: it is a preprint, muscle CSA was estimated from circumference plus skinfold rather than imaging, and 27.5 % of randomised participants did not complete post-testing. Under the β = 1.90 curve, 9 → 36 sets predicts 1.90(√36 − √9) = 5.7 pp — the trial did not detect it.
  - evidence: https://sportrxiv.org/index.php/server/preprint/view/810 — abstract, sample, and equivalence statistics as fetched 2026-08-18.
  - implication: Ship the volume curve with an explicit uncertainty band (β ∈ 1.08…2.38) and attach this trial as `counterEvidence` on the volumeDoseResponse claim. Any UI that says 'add sets to grow more' must be able to show, in one tap, the best trial that failed to find that effect. This is exactly the brand wedge — no competitor shows you the study that disagrees with their own model.
- **The ACSM Position Stand published April 2026 is the most authoritative current source and is newer than everything in the prior research digest; it endorses ≥10 sets/week, ≥2 sessions/week, and explicitly finds training to failure, set structure, time under tension, and periodization not consistently impactful.** _(high)_
  - detail: "Resistance Training Prescription for Muscle Function, Hypertrophy, and Physical Performance in Healthy Adults: An Overview of Reviews", Med Sci Sports Exerc 2026;58(4):851-872, DOI 10.1249/MSS.0000000000003897, PMID 41843416; chaired by Stuart M. Phillips with Currier, D'Souza, Fiatarone Singh, Rawson, Schoenfeld, Smith-Ryan, Steen, Thomas, Triplett, Washington, Werner. First update since 2009; umbrella review of 137 systematic reviews and >30,000 participants. Abstract recommendations: strength ≥80 % 1RM, 2–3 sets, ≥2 sessions/wk; hypertrophy ≥10 sets/wk; power 30–70 % 1RM. Explicit: "Training to momentary muscle fatigue, equipment type, exercise complexity, set structure, time under tension, blood flow restriction, and periodization did not consistently impact training outcomes."
  - evidence: PMID 41843416; DOI 10.1249/MSS.0000000000003897; abstract retrieved via Europe PMC 2026-08-18; author list and methodology confirmed at https://acsm.org/science-spotlight-acsm-releases-new-position-stand-on-resistance-training/.
  - implication: This is the citation for the app's defaults and for four of the claims it must stop making. It also sets the honest headline: 10 sets/muscle/week, twice a week, not to failure, done consistently — and the app's job is to make that easy to execute, not to sell precision beyond it.
- **Frequency must stop being a scored dimension: the app's current frequency tip states something the best available evidence contradicts, and the honest justification for splitting volume across days is the per-session cap, not frequency itself.** _(high)_
  - detail: FrequencyScorer emits, verbatim, "all N sets land on one day. Splitting them across 2 sessions builds more muscle at the same weekly volume" and assigns quality 0.55 for that case. Pelland 2025 found the hypertrophy frequency marginal slope = 0.32 % [95 % CrI −0.14, 0.82] with only 91.3 % posterior probability of exceeding zero — the credible interval contains the null. Strength is the opposite: 3.27 % [2.74, 3.84], 100 % probability, reciprocal fit. The defensible reason to spread volume is Remmert et al.'s per-session point of undetectable outcome superiority at ~11 fractional sets per session for hypertrophy (~2 direct sets for strength). Replacement rule, fully specified: `sessionsNeeded(forWeeklySets v: Double) -> Int = max(1, Int(ceil(v / 11.0)))`, surfaced as a structural constraint on the split builder, not as a score. TrainingScience.targetWeeklyFrequency = 2 survives only as the ACSM/strength default, tagged accordingly.
  - evidence: FrequencyScorer.swift:40-53 (message and 0.55 quality); TrainingScience.swift:238-240 (comment: "Training a muscle twice a week beats once at matched weekly volume — the best-supported frequency finding"); TemplateQualityEngine.swift:25 (weight 0.13); Pelland 2025 §3.5.1 and §3.5.2; Remmert JF et al., "Is There Too Much of a Good Thing? Meta-Regressions of the Effect of Per-Session Volume on Hypertrophy and Strength", SportRxiv preprint 537, https://sportrxiv.org/index.php/server/preprint/view/537.
  - implication: Delete FrequencyScorer as a scored dimension and its 0.13 weight; fold the per-session cap into the volume model where it belongs. Keep a 2×/week default because ACSM 2026 recommends it and because it satisfies the cap for any muscle above 11 weekly sets — but never claim it grows more muscle at matched volume.
- **The neutral-70 fallback exists at eight call sites and must be eliminated at the type level with an `Assessed<Value>` enum in which unknown propagates to unknown; a defaulted Int can always be laundered into a passing grade, an enum cannot.** _(high)_
  - detail: Every scorer returns `DimensionScore(dimension:…, score: 70, tips: [])` when it has nothing to grade: BalanceScorer.swift:21, FatigueScorer.swift:23, FrequencyScorer.swift:28, RepRestScorer.swift:12, SelectionScorer.swift:12, VolumeScorer.swift:22/:102/:151. Allow it to widen guardrails; never allow it to add or remove load by itself.** — Logged RIR is the single most useful signal the app can collect and the most systematically biased. Calibrating it and showing the user their own bias is a genuinely novel, cited feature; letting it silently drive load would repeat the pseudo-precision mistake the product is meant to avoid.
- [days] **Replace the deload trigger with an opt-in maintenance mode: after two consecutive weeks below 50 % of planned sets, offer ~1/3 volume at unchanged loads, citing Bickel 2011 with the explicit caveat that the result held for young adults and not for 60–75 year olds. Never auto-generate make-up sets for a skipped session; report achieved sets and the tier those achieved sets fall in.** — The only controlled deload trial found no benefit and a small edge for continuous training, while the maintenance result is well-evidenced and maps to a real user need (travel, illness, exams) that no mainstream competitor addresses.
- [days] **Fix the muscle-attribution map before it feeds the new curve: repair the bare-'shoulders' → sideDelts mapping, and add a catalog-walking test (in the style of the existing CatalogMuscleCoverageTests) that asserts every shipped catalog and equipment record resolves to a primary muscle and that no record credits side delts purely from a bodyParts fallback.** — Under v2 the entire volume model is one curve, so every number the user sees is determined by the attribution map. A systematic side-delt inflation that is currently one wrong tip becomes, in v2, a wrong dose recommendation for every pressing movement.
- [weeks] **Extract the whole engine as a standalone Swift package with no app-layer types, injecting the equipment lookup rather than calling `EquipmentDatabase.find` globally, and adopt Swift 6.3 strict concurrency with every engine type `Sendable` and every function pure. Move all user-facing copy out of the scorers into a rendering layer keyed by ClaimID.** — Structured tips keyed by ClaimID are a prerequisite for the honesty layer's third enforcement test, and a pure, Sendable, dependency-free package is what makes the engine testable at speed, portable to a Watch target, and eventually publishable — which is itself a credibility asset for a science-positioned product.

### Risks
- β = 1.90 is my fit to Pelland's published tier table, not a parameter the authors reported. It reproduces their four increments to within 0.5 sets and sits inside their marginal-slope credible interval, but it is a reconstruction and should be labelled as such in the code comment and in the evidence entry. If the authors' supplementary model files (osf.io/6z3xu) give the actual fitted coefficients, use those instead.
- Steele et al. 2026 (9 vs 36 fractional sets equivalent) is a preprint with a crude outcome measure — CSA estimated from circumference and skinfolds — and 27.5 % of randomised participants missing post-testing. Treating it as decisive would be as wrong as ignoring it. It belongs in the counterEvidence array, not as a reason to flatten the curve.
- The ACSM 2026 numbers were read from the abstract and from ACSM's own announcement pages, not from the full position stand. The specific figures (≥10 sets/wk, 2–3 sets at ≥80 % 1RM, ≥2 sessions/wk) should be verified against the published article before they are quoted in-product.
- The Marzagão weight-dependent equation's unit basis is unresolved. My numerical evidence points to pounds, but that is inference from a curve fit, not a statement in the paper. Shipping it against kilogram inputs would inflate every dumbbell and cable e1RM by 12–45 % — a worse error than the formula it replaces.
- Removing per-muscle bands, the experience multiplier, MRV, and the fatigue dimension all at once strips out most of what currently makes the engine look sophisticated to a casual user. The replacement must feel like more insight, not less: if 'how many sets' collapses to one curve, the marginal-value-per-set and time-cost readouts have to carry the perceived depth.
- An `Assessed` type that refuses to score is only an improvement if the app can usually resolve exercises. If the muscle-attribution map has poor coverage on brand machines and custom lifts, the honest engine will say 'I don't know' constantly and read as broken. Coverage of the shipped catalog must be measured before the refusal thresholds (0.70 / 0.85) are finalized.
- The honesty positioning invites scrutiny of exactly the numbers being shipped. Every constant that survives — 11 sets/session, the 2.5 % PR threshold, the k = 5 shrinkage weight, the 5 % back-off, the 0.70 coverage floor — is an app heuristic with no citation and must be labelled `.heuristic` rather than quietly presented alongside the cited ones.
- None of this can be verified by running the existing test suite in this environment: xcodebuild has no pty here per project memory, so all code claims above are by inspection and by local simulation of the shipped constants, not by execution. Establish an authoritative serial run (-parallel-testing-enabled NO) before treating any of the existing 365 tests as a safety net for the rewrite.

### Open questions
- Should the app show the marginal value of the next set in percentage points of muscle size at all? It is the most honest expression of the evidence, but 'this set buys you 0.19 percentage points' may read as absurd precision to a lifter and invite exactly the pseudo-precision criticism the product is trying to avoid. The alternative is a purely ordinal 'high / moderate / low return' readout.
- Does the product keep any single headline number? Killing the 0–100 composite is defensible but removes the app's most gamifiable surface. A defensible middle path is to keep an internal ordinal score for ranking auto-fixes and to show only per-dimension verdicts plus one 'biggest lever' — but that is a product bet, not an evidence question.
- Given ACSM 2026's core message that adherence beats optimization, how far does the app go toward optimizing at all? There is a coherent product where the engine's main job is coverage and consistency, and the dose curve is a secondary explanation rather than the headline.
- Should the strength path share the volume model? The strength tiers are much flatter (MED 1 set, no consistent gain past 5) and the best-fit model is reciprocal, not square-root. Supporting both means two curves, two SDES values, and a goal switch that changes every number the user sees.
- Is a per-user volume preference multiplier retained in any form? The evidence says individual response variation has repeatedly failed to be detected, so the honest framing is 'your preference', not 'your optimum' — but users will expect the app to personalize, and the copy has to carry that distinction without sounding evasive.
- Does the app collect an explicit 'I went to failure on this set' flag? The RIR calibrator needs it, but it adds a tap to the logging flow — and the prior competitive research found that logging craft and tap count outrank science depth in user reviews.
- Should the engine ship as an open-source Swift package? It would be strong evidence for the honesty positioning and would make the claims auditable, but it also hands the one genuinely differentiated asset (the volume model plus the attribution map) to competitors.

## watchOS 26 + HealthKit standalone lifting app: architecture, sync, input, HealthKit limits, and v1 scope verdict

**Summary.** The Watch app is v1 scope, but a much smaller v1 than "port the phone app to the wrist." The review complaint being removed is binary — reviewers write "no Apple Watch app," not "the Watch app lacks charts" — so a deliberately minimal, correct Watch app captures nearly all of the rating value. Budget 7–9 calendar weeks solo, of which ~2 weeks is on-device testing that cannot be shortened (WatchConnectivity transfers, Always-On behavior, and background haptics do not work in the simulator).

The single strongest technical argument for the Watch is not heart rate — it is the rest timer. On watchOS, `WKInterfaceDevice.play(_:)` is blocked in the background, and dropping your wrist backgrounds the app even though Always-On keeps pixels lit. The only documented exemption is an active `HKWorkoutSession` (Apple DTS, forums/thread/772780). So a live workout session plus `UIBackgroundModes: [audio]` is what makes a wrist haptic at rest-end actually fire. Elos today fakes this on iPhone with a local notification (Utils/NotificationManager.swift:83) — that is the mechanism competitors get 1-starred over.

For sync, the correct answer is: Watch owns a local SwiftData store with `cloudKitDatabase: .none`, and reconciles to the phone over `transferUserInfo` with client-generated, immutable set IDs. CloudKit on watchOS is actively dangerous here — FB17685611 documents watch app termination 30–60 s in when Always-On is off and the phone is unreachable, which is precisely the basement-gym case. `sendToRemoteWorkoutSession` hangs without completion in ~5% of workouts (forums/thread/769355), so it may only carry live-mirror niceties, never durable set data. `updateApplicationContext` coalesces and would silently drop sets. Make the merge order-independent and idempotent, not delivery-ordered.

On HealthKit, be honest about a hard ceiling: as of iOS/watchOS 26 there is **no** quantity type for reps, sets, weight lifted, or volume — verified against the full `HKQuantityTypeIdentifier` list. Per-set data lives only in your store. The one real integration win nobody ships is `relateWorkoutEffortSample` — writing session (and per-exercise) RPE into Apple's Training Load. Elos already collects `sessionRPE` (SwiftData/ElosSchema.swift:145) and throws it away.

### Findings
- **Background haptics on watchOS are blocked unless an HKWorkoutSession is active — this, not heart rate, is the load-bearing reason a lifting app needs a Watch target.** _(high)_
  - detail: Apple's `WKInterfaceDevice.play(_:)` documentation states you cannot play haptic feedback in the background, with apps running an active workout session as the only exception. An Apple DTS engineer (Ziqiao Chen) confirmed in forums/thread/772780 that this is as-designed, not a bug: when the wrist lowers, the app backgrounds even though Always-On keeps the UI visible, and beeps/haptics stop. Adding generic background modes does not help — it works in the simulator and fails on device. The required combination is `WKBackgroundModes = ["workout-processing"]` (for background execution) AND `UIBackgroundModes = ["audio"]` (for haptics/audio from background) in the Watch app's Info.plist, plus a running HKWorkoutSession.
  - evidence: https://developer.apple.com/forums/thread/772780 ; https://developer.apple.com/documentation/HealthKit/running-workout-sessions ; https://developer.apple.com/documentation/watchkit/enabling-background-sessions
  - implication: The rest timer — the #1 thing competitors lose stars over — is only fully trustworthy on the Watch, and only if you run a real HKWorkoutSession. Make HKWorkoutSession non-optional in the Watch app even for users who don't care about heart rate; it is the runtime permit for the timer, not a health feature.
- **There is no separate "workout-session entitlement" — the requirement is the HealthKit capability plus two Info.plist background-mode keys.** _(high)_
  - detail: The concrete, complete list for a standalone lifting Watch app: entitlement `com.apple.developer.healthkit = true` (Xcode HealthKit capability); Info.plist `NSHealthShareUsageDescription` and `NSHealthUpdateUsageDescription`; `WKBackgroundModes` array containing exactly `workout-processing` (Apple documents this as the only allowed value for that key); `UIBackgroundModes` array containing `audio` if you play haptics or sound. `com.apple.developer.healthkit.access` is only needed for clinical records and must NOT be requested. Extended-runtime modes (`self-care`, `mindfulness`, `physical-therapy`, `alarm`) are mutually exclusive with each other but can coexist with `workout-processing` — irrelevant here, since a lifting app should use HKWorkoutSession, not WKExtendedRuntimeSession.
  - evidence: https://developer.apple.com/documentation/bundleresources/information-property-list/wkbackgroundmodes ; https://developer.apple.com/documentation/watchkit/enabling-background-sessions ; https://developer.apple.com/documentation/HealthKit/running-workout-sessions
  - implication: No provisioning-profile special request or Apple approval is on the critical path. This removes a scheduling risk from the plan: the Watch app can be started week 1 without waiting on Apple.
- **HealthKit has no quantity type for reps, sets, weight lifted, or training volume as of iOS/watchOS 26 — per-set strength data is unrepresentable in Health.** _(high)_
  - detail: Reading the complete `HKQuantityTypeIdentifier` case list from Apple's documentation: the Activity category (41 cases) covers running/cycling/swimming/rowing/paddle/ski metrics, energy, VO2max, physicalEffort, workoutEffortScore and estimatedWorkoutEffortScore — and nothing for repetitions, sets, load, or resistance volume. Body Measurements, Vital Signs and Mobility contain nothing applicable either. Separately, `HKMetadataKeyWeight` does not exist; the workout metadata keys are swim/cycling/weather/lap oriented (`HKMetadataKeyLapLength`, `HKMetadataKeySwimmingStrokeStyle`, `HKMetadataKeyIndoorWorkout`, `HKMetadataKeyWorkoutBrandName`, `HKMetadataKeyElevationAscended`, …). watchOS 27's new workout-zones API covers heart rate and cycling power only — explicitly nothing for strength.
  - evidence: https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier ; https://github.com/Mylittleswift/ios-health-fitness-apps/blob/master/HealthKit.framework/HKMetadata.h ; https://developer.apple.com/videos/play/wwdc2026/207/
  - implication: Do not plan any feature that assumes strength data round-trips through Health. Your SwiftData store is the sole source of truth for sets. Corollary: HealthKit is not a viable sync bus between Watch and phone for set data, which forces the WatchConnectivity design.
- **`relateWorkoutEffortSample` is the one genuinely differentiating HealthKit write available to a lifting app, and it must not be called through the normal sample-add path.** _(high)_
  - detail: iOS 18 added a 1–10 workout effort score that feeds Apple's Training Load chart in Fitness. Writing it requires `HKQuantitySample(type: HKQuantityType(.workoutEffortScore), quantity: HKQuantity(unit: .appleEffortScore(), doubleValue: rpe), start:end:)` followed by `healthStore.relateWorkoutEffortSample(sample, with: workout, activity: nil)`. Using `HKWorkoutBuilder.add([samples])` or `HKHealthStore.add(_:to:)` fails with "Sample of type HKQuantityTypeIdentifierWorkoutEffortScore must be related to a workout." The `activity:` parameter accepts an `HKWorkoutActivity`, so per-exercise RPE is expressible, not just per-session. `.workoutEffortScore` must be in the requested share types.
  - evidence: https://sasq.ca/blog/2025/4/28/reading-writing-workout-effort-scores ; https://developer.apple.com/forums/thread/763539 ; SwiftData/ElosSchema.swift:145,196-197
  - implication: Elos already collects `sessionRPE` (SwiftData/ElosSchema.swift:145) and per-set RPE/RIR (SwiftData/ElosSchema.swift:196-197) and writes neither. Piping RPE into Apple's Training Load is a one-day feature that no science-lifting competitor ships and that shows up in Apple's own Fitness UI — free credibility surface.
- **SwiftData + CloudKit on watchOS terminates the app in exactly the basement-gym scenario; the Watch store must be configured `cloudKitDatabase: .none`.** _(high)_
  - detail: FB17685611 (developer.apple.com/forums/thread/785378): with Always-On Display OFF and the iPhone disconnected or in Airplane Mode, CloudKit setup registers an unmanaged long-running background task ("Background Task (\"CoreData: CloudKit Setup\"), was created over 30 seconds ago") and the watch app is terminated 30–60 s into the session. An Apple Frameworks Engineer acknowledged the report; no fix shipped as of the thread. The workaround is `ModelConfiguration(schema: schema, cloudKitDatabase: .none)`. Related reports show SwiftData+CloudKit simply not initializing on watchOS at all (forums/thread/733397) and container conflicts when the same schema is used by a watch app and a widget extension (forums/thread/733129).
  - evidence: https://developer.apple.com/forums/thread/785378 ; https://developer.apple.com/forums/thread/733397 ; https://developer.apple.com/forums/thread/733129
  - implication: Rules out "shared CloudKit store" as the Watch↔phone sync design. The Watch gets a local-only SwiftData store; CloudKit, if used at all, stays on the iPhone side. Also means the widget/complication extension must not share the watch's CloudKit-backed container.
- **App Groups do not share a container between Watch and iPhone — they have not since watchOS 2 — so there is no "shared SQLite file" option at all.** _(high)_
  - detail: Apple's guidance: watch apps that shared data with their iOS apps using a shared group container must be redesigned; from watchOS 2 onward each process manages its own copy of shared data in its local container, and data updated by both sides must move through WatchConnectivity. App Groups on watchOS are still used for sharing between the watch app and its own widget extension, but never across the device boundary.
  - evidence: https://developer.apple.com/forums/thread/7440 ; https://developer.apple.com/forums/thread/133251
  - implication: The design space for Watch↔phone reconciliation is exactly three options — WatchConnectivity, CloudKit (ruled out above for watchOS), or each device syncing independently to your backend. Do not spend time investigating a shared file.
- **`transferUserInfo` is the only correct durable channel for logged sets; `updateApplicationContext` silently drops data and `sendMessage` requires reachability.** _(high)_
  - detail: `transferUserInfo(_:)` is a FIFO, persisted queue: every payload is delivered in order, survives app termination and reboot, and is delivered in the background when the counterpart becomes available. `updateApplicationContext(_:)` holds exactly one slot — sending a new dictionary before the previous one transmits replaces it entirely, so a burst of set logs coalesces into one and the rest are lost. `sendMessage(_:replyHandler:)` fails immediately when `WCSession.isReachable == false`. Also: the watchOS Simulator does not implement `transferUserInfo(_:)`, `transferFile(_:metadata:)` or `transferCurrentComplicationUserInfo(_:)` — these can only be tested on paired hardware.
  - evidence: https://www.kodeco.com/books/watchos-with-swiftui-by-tutorials/v1.0/chapters/4-watch-connectivity ; https://medium.com/@sheik25bareeth/data-synchronization-between-ios-and-watchos-using-watchconnectivity-009a3064e12a
  - implication: Concrete channel assignment: sets and tombstones → `transferUserInfo`; "today's plan" and "acked client-IDs" from phone → `updateApplicationContext` (idempotent state, correct fit); end-of-session full JSON blob → `transferFile` as belt-and-braces; live "in progress" UI mirroring → `sendMessage`/`sendToRemoteWorkoutSession`, best-effort only. And budget device-testing time: this layer cannot be developed in the simulator.
- **`sendToRemoteWorkoutSession` hangs with no success and no error in roughly 5% of workouts, for the whole session, on watchOS 10/11 and iOS 17/18 — it cannot carry durable data.** _(high)_
  - detail: developer.apple.com/forums/thread/769355: a developer with thousands of daily workouts sending messages every few seconds reports that `try await workoutSession.sendToRemoteWorkoutSession(data:)` neither returns nor throws in ~5% of sessions; when it happens the channel stays broken for the entire workout, and in rare cases errors surface 30+ minutes later. The only known remedy is rebooting both devices. No Apple response documented. The code path follows Apple's own "Building a Multidevice Workout App" sample.
  - evidence: https://developer.apple.com/forums/thread/769355
  - implication: HealthKit mirroring is a live-display convenience, not a sync protocol. Wrap every call in a timeout (e.g. a `Task` cancelled after 3 s) so the UI never blocks on it, and never mark a set as "delivered" on the strength of a mirroring send. Every set must still go through `transferUserInfo`.
- **In HealthKit mirroring the Watch is always the primary and the iPhone is the mirror — the direction is fixed and cannot be inverted.** _(high)_
  - detail: `HKWorkoutSession.startMirroringToCompanionDevice(completion:)` is called on the watch session; the iPhone is notified via `HKHealthStore.workoutSessionMirroringStartHandler` and receives an `HKWorkoutSession` whose `type` is `.mirrored`. Bidirectional payloads use `sendToRemoteWorkoutSession(data:completion:)` and arrive at `workoutSession(_:didReceiveDataFromRemoteWorkoutSession:)`. Requires iOS 17 / watchOS 10+. To start from the phone side you instead call `healthStore.startWatchApp(toHandle: configuration)`, which launches the Watch app and delivers the configuration to its `handle(_ workoutConfiguration:)`. Known pitfall: sending data to the remote session before it is started produces "Remote session delegate is not set up."
  - evidence: https://developer.apple.com/documentation/healthkit/hkworkoutsession/startmirroringtocompaniondevice(completion:) ; https://developer.apple.com/documentation/healthkit/hkhealthstore/workoutsessionmirroringstarthandler ; https://sasq.ca/blog/2025/3/2/building-a-workout-app-for-apple-watch ; https://nonstrict.eu/blog/2024/hkworkoutsession-remote-delegate-not-setup-error/
  - implication: Design the state machine as watch-authoritative-when-present. Phone "Start workout" calls `startWatchApp(toHandle:)` rather than opening a phone-side session, so there is exactly one session object in the system and no double-logging ambiguity.
- **Apple's own sample code gets the session-teardown order wrong; calling `builder.endCollection` before `session.end()` awaits forever.** _(medium)_
  - detail: Correct order is `session?.end()` first, then `try await builder.endCollection(at: date)`, then `finishedWorkout = try await builder.finishWorkout()`. The reverse (Apple's sample, and the ordering implied in the older "Running workout sessions" article where `endCollection` is called from the `.stopped` delegate callback and `session.end()` last) can await indefinitely because the session never reaches ended. The two are reconcilable — the doc's version calls `endCollection` on the `.stopped` transition, not on `.ended` — but the async/await rewrite is where it bites.
  - evidence: https://sasq.ca/blog/2025/3/2/building-a-workout-app-for-apple-watch ; https://developer.apple.com/documentation/HealthKit/running-workout-sessions
  - implication: Write the teardown once, in the shared engine, with an explicit ordering comment and a unit test on the state machine. A hang here means a lost workout, which is the single worst failure mode in this category (documented at Boostcamp, JuggernautAI, MacroFactor).
- **An active HKWorkoutSession grants background runtime but the app is still killed for CPU overrun — Always-On rendering must be throttled deliberately, not incidentally.** _(high)_
  - detail: Apple Frameworks Engineer in forums/thread/723786: apps with `WKBackgroundModes: workout-processing` still get suspended when the system logs "CPU time was exceeded"; the reporter hit this after migrating WatchKit→SwiftUI because the SwiftUI implementation did more per-tick work. Rendering rules: in the Always-On state a workout app may update its UI at most about once per second; `@Environment(\.isLuminanceReduced)` becomes true when the wrist drops; Apple's guidance is to remove time-sensitive counters, hide private information, and resolve animations to a rested frame rather than leaving them mid-loop. A shipping watch app (Tooboo) reports 12–16 h battery by running map render, UI update and algorithm on independent schedules and dropping refresh from 1 Hz to once per 10–20 s when luminance is reduced.
  - evidence: https://developer.apple.com/forums/thread/723786 ; https://fatbobman.com/en/posts/watchos-development-pitfalls-and-practical-tips ; https://developer.apple.com/videos/play/wwdc2021/10002/
  - implication: Concrete rule for the build: put the countdown inside a `TimelineView(.periodic(from: start, by: isLuminanceReduced ? 10 : 1))` scoped to the smallest possible subview; render minutes-only when luminance is reduced; never recompute the exercise list or any engine calculation on the tick. Verify with Instruments on device, not in the simulator.
- **Crash/relaunch recovery must be triggered manually at launch — `handleActiveWorkoutRecovery` does not fire after a device reboot.** _(medium)_
  - detail: Apple's documented path is `WKExtensionDelegate.handleActiveWorkoutRecovery()` → `healthStore.recoverActiveWorkoutSession { session, error in ... }`, after which you must re-fetch `session.associatedWorkoutBuilder()`, reassign delegates and rebuild the `HKLiveWorkoutDataSource`. Field report (fatbobman, Tooboo): the delegate callback does not trigger after a reboot, so the app must call `recoverActiveWorkoutSession()` unconditionally on every launch, and any custom in-session state beyond what HealthKit stores (your logged sets, current exercise index, rest-timer end date) must be re-derived from your own persisted store.
  - evidence: https://fatbobman.com/en/posts/watchos-development-pitfalls-and-practical-tips ; https://developer.apple.com/documentation/HealthKit/running-workout-sessions ; SwiftData/ElosSchema.swift:151-154 ; Views/ActiveSessionView.swift:15-21
  - implication: Persist the in-progress session to the Watch's SwiftData store on every set log, not at session end. Elos already proves the pattern on iPhone with `WorkoutSessionRecord.draftJSON` (SwiftData/ElosSchema.swift:154) and the wall-clock `restEndsAt` anchor (Views/ActiveSessionView.swift:21) — carry both concepts to the Watch and make `restEndsAt` part of the persisted draft.
- **The Digital Crown must be the edit path, not the entry path, and its detent should be the plate increment — plus `focusable()` has an ordering trap.** _(high)_
  - detail: Signature: `digitalCrownRotation(_ binding: Binding<V>, from: V, through: V, by: V.Stride?, sensitivity: DigitalCrownRotationalSensitivity, isContinuous: Bool, isHapticFeedbackEnabled: Bool)`. Concrete parameters for lifting: reps `from: 0, through: 50, by: 1, sensitivity: .low, isContinuous: false, isHapticFeedbackEnabled: true`; weight `by:` set to the resolved plate increment (2.5 kg / 5 lb, 1.25 kg for micro-plates), so one detent equals one real plate change rather than a meaningless 0.1. Trap: placing `.focusable()` after `.digitalCrownRotation()` silently disables crown tracking — `.focusable()` must come first. Crown detents already emit system haptics via `isHapticFeedbackEnabled`.
  - evidence: https://developer.apple.com/documentation/swiftui/view-input-and-events ; https://www.hackingwithswift.com/quick-start/swiftui/how-to-read-the-digital-crown-on-watchos-using-digitalcrownrotation ; https://www.kodeco.com/books/watchos-with-swiftui-by-tutorials/v1.0/chapters/3-digital-crown
  - implication: Set the interaction budget explicitly: the prefilled last-session value plus a single tap must be the whole common path (zero crown turns), matching the ≤3-tap rule the prior UX teardown established. Reserve the crown for the 10–20% of sets that deviate.
- **Double tap is a single, scene-scoped primary action — `.handGestureShortcut(.primaryAction)` on watchOS 11.0+ — and it must be re-bound as the session state changes; wrist flick has no third-party API.** _(high)_
  - detail: `nonisolated func handGestureShortcut(_ shortcut: HandGestureShortcut, isEnabled: Bool = true) -> some View`, availability watchOS 11.0+ / iOS 18.0+, hardware Series 9 / Ultra 2 and later. It applies to Button and Toggle; the target is resolved in a leading-to-trailing traversal of the active scene, so effectively one control wins. The system outlines the winning control automatically when the gesture is performed. watchOS 11 extended double tap into Lists, ScrollViews and vertical TabViews. Double tap is the only gesture third-party apps can respond to — the others are reserved for AssistiveTouch. The watchOS 26 wrist-flick gesture is system-only (dismiss notification, silence timer, return to face); no developer API surfaced.
  - evidence: https://developer.apple.com/documentation/SwiftUI/View/handGestureShortcut(_:isEnabled:) ; https://developer.apple.com/videos/play/wwdc2024/10205/ ; https://www.apple.com/newsroom/2025/06/watchos-26-delivers-more-personalized-ways-to-stay-active-and-connected/
  - implication: Bind `.primaryAction` state-dependently: during a set it is "Log set"; during rest it is "Skip rest"; after the last set of an exercise it is "Next exercise." Use `isEnabled:` to guarantee exactly one active binding. This is the concrete one-handed, chalked-hands story that no competitor advertises.
- **watchOS 26 replaces ClockKit with WidgetKit, adds native watch `ControlWidget`, adds APNs widget push, and adds RelevanceKit for Smart Stack surfacing.** _(high)_
  - detail: From WWDC25 session 334: ClockKit complications are deprecated in favour of WidgetKit, which now supports push updates via APNs on every WidgetKit platform including watchOS. `ControlWidget` with `AppIntentControlConfiguration` now works natively on watchOS — controls appear in Control Center, the Smart Stack, and the Action button on Apple Watch Ultra. RelevanceKit introduces `RelevanceConfiguration(kind:provider:)`, `RelevanceEntriesProvider`, `WidgetRelevance`, `WidgetRelevanceAttribute` and `RelevantContext` (date, sleep schedule, fitness information, location POI categories such as `.beach`/`.grocery`/`.cafe`). Apple also states that to get good Smart Stack workout suggestions you must use the correct `HKWorkoutActivityType` and accurate start/end times. Series 9+ and Ultra 2 are now arm64 — build with "Standard Architecture" and test on device, since Float/Int/pointer math differs from the simulator.
  - evidence: https://developer.apple.com/videos/play/wwdc2025/334/ ; https://developer.apple.com/videos/play/wwdc2025/278/
  - implication: Ship one `accessoryCircular`/`accessoryCorner` complication ("Push Day — Start") and one Ultra Action-button `ControlWidget`. Skip RelevanceKit in v1: whether a gym/fitness POI category is exposed to third parties is unverified, and the payoff is speculative. Note the arm64 item as a real testing requirement, not a formality.
- **Apple Watch does not sample HRV during workouts — in-session HRV is not obtainable, and strength-training energy may currently be miscalculated by the framework itself.** _(high)_
  - detail: `heartRateVariabilitySDNN` exists as a quantity type, but Apple Watch writes SDNN from Mindfulness/Breathe sessions (where the user is guided to remain still for a minute or more) and from opportunistic background reads — not continuously and not during workouts. Independent analysis (Marco Altini) notes the criteria for background SDNN writes are undocumented and inconsistent outside Breathe. Separately, developers report (forums/thread/792607) that `HKLiveWorkoutBuilder` returns wrong calorie data specifically when `activityType` is `.traditionalStrengthTraining` or `.jumpRope` on iOS 26, while walking/running are correct.
  - evidence: https://medium.com/@altini_marco/on-heart-rate-variability-and-the-apple-watch-24f50e8e7bc0 ; https://developer.apple.com/forums/thread/792607 ; Services/HealthKitService.swift:16-21,42-50
  - implication: Two honesty constraints, both consistent with the prior EvidenceLibrary posture: (1) show HRV only as an overnight/morning trend, explicitly labelled as not measured during the session, and never let it prescribe sets or load; (2) verify strength-training energy on a real device against Apple's Workout app before launch, and if it is still wrong, present energy as an estimate rather than a headline. Do NOT hand-roll kcal on the Watch — Elos's `HealthEnergy.estimateKcal` (Services/HealthKitService.swift:42) is right for the phone-only export path and wrong once a live builder exists.
- **`HKWorkoutActivity` is the only structural hook for per-exercise segmentation, and it is per-exercise, not per-set.** _(high)_
  - detail: `HKWorkoutActivity` (watchOS 9.0+ / iOS 16.0+) partitions a workout into segments; Apple's documented use cases are multisport legs and interval work/rest periods. Its designated initializer is `init(workoutConfiguration:start:end:metadata:)`, and on a live session you create them with `HKWorkoutSession.beginNewActivity(configuration:date:metadata:)` / `endCurrentActivity(on:)`. Each carries free-form `metadata: [String: Any]`, `allStatistics` and `workoutEvents`. Every `HKWorkout` has at least one activity, auto-created if you set none. Custom metadata keys survive a round trip but nothing in the Health app or any other app renders them.
  - evidence: https://developer.apple.com/documentation/healthkit/hkworkoutactivity ; https://developer.apple.com/documentation/healthkit/hkworkoutsession
  - implication: Map one activity per exercise (a 20-set / 6-exercise session = 6 activities, safely within reason), attach per-exercise effort with `relateWorkoutEffortSample(_:with:activity:)`, and store your own set detail in reverse-DNS metadata (`com.<bundle>.exercise`, `com.<bundle>.topSetKg`) purely as a self-recovery backup. Do not market it as Health integration — no third party can read it meaningfully.
- **The greenfield merge key must be a client-generated immutable ID plus a per-device revision counter — timestamps and delivery order are both unsafe across Watch and phone.** _(high)_
  - detail: Elos already has half of this: `ExerciseSetRecord.id` is a client-generated UUID string (SwiftData/ElosSchema.swift:189, default `UUID().uuidString` at :226) with `serverID` and `syncPending` for the phone→server leg (:200-201), and the same pattern on `WorkoutSessionRecord` (:149-150). What is missing for a three-way merge is a `deviceID` and a monotonic `revision: Int`. Ordering cannot be inherited from `transferUserInfo`'s FIFO guarantee, because that queue does not survive a phone restore or a reinstall, and a mid-session hand-off can interleave watch-logged and phone-logged sets. Wall-clock tiebreaks are unsafe because the Watch and phone clocks are independently set.
  - evidence: SwiftData/ElosSchema.swift:189,200-201,226 ; SwiftData/ElosSchema.swift:149-150
  - implication: Concrete schema for the new app: `SetRecord { clientID: UUID (immutable, minted at log time on the logging device), sessionClientID: UUID, exerciseInstanceID: UUID, setIndex: Int, deviceID: String, revision: Int, loggedAtSessionOffset: TimeInterval, deleted: Bool }`. Merge is an idempotent upsert keyed on `clientID`, ordered by `(exerciseInstanceID, setIndex)`, conflicts resolved by `(revision, deviceID)` — never by date. Backend needs `client_id UNIQUE` and a tombstone column, which the current Elos API entirely lacks.
- **The Elos active-session state machine is 647 lines of SwiftUI `@State` and is not portable to the Watch as written — extracting it into a pure engine is the one hard precondition for the Watch app.** _(high)_
  - detail: `Views/ActiveSessionView.swift` holds the whole machine in view state: `restSeconds`, `restTotalSeconds`, `restActive`, `restPaused`, `restEndsAt`, `activeExerciseId`, `undoInfo` (lines 11-28), a `Timer.publish(every: 1)` (:38), and the mutation functions `adjustRest` (:333), `skipRest` (:344), rest pause (:356) and the completion branch (:87). `Features/ActiveWorkout/ActiveWorkoutViewModel.swift` and `ActiveWorkoutView.swift` are one-line stubs containing only `import Foundation`. The one genuinely good piece is already there: the countdown derives from a wall-clock `restEndsAt` anchor rather than decrementing per tick, with a comment (:16-21) explaining that `Timer.publish` does not fire while backgrounded. The project has three targets only — Elos, ElosTests, ElosUITests — `SDKROOT = iphoneos`, `IPHONEOS_DEPLOYMENT_TARGET = 18.0`, and zero files importing WatchConnectivity, WidgetKit, ActivityKit or HKWorkoutSession.
  - evidence: Views/ActiveSessionView.swift:11-28,38,87,333-362 ; Features/ActiveWorkout/ActiveWorkoutViewModel.swift:1 ; /Users/frankbisignano/dev/elos/apps/elos-mobile/Elos/Elos.xcodeproj/project.pbxproj:103-172,339
  - implication: Structure the new app as a Foundation-only SPM core (`SessionEngine`, `RestClock`, `SetLog`, `MergeResolver` — pure value types, no SwiftUI) consumed by both the iOS and watchOS targets, exactly as the existing 4,706-line Intelligence/ layer is structured. Keep the `restEndsAt` wall-clock anchor. This costs ~1 week if done first and roughly 3–4 weeks if retrofitted.
- **"Standalone" in the review-complaint sense means "works with the phone in the locker," not "separate App Store SKU" — and shipping it as a separate SKU would be a mistake.** _(medium)_
  - detail: Competitor testing (2026) separates the two clearly: Strong and Gymaholic run complete independent sessions on-wrist; Hevy's Watch app "syncs live with phone", requires phone connectivity, and is criticised for lagging when syncing; Ladder is phone-dependent with no standalone capability. None of these are separately purchased apps — they are single-purchase apps whose Watch component happens to function without reachability. Making the Watch app an independent App Store product would fork the subscription ledger and the review queue for zero user benefit.
  - evidence: https://www.findyouredge.app/news/best-strength-training-apps-apple-watch-2026 ; https://www.findyouredge.app/news/best-strength-training-apps-2026
  - implication: Ship the Watch app embedded in the iOS app bundle (single-target Watch App with `WKCompanionAppBundleIdentifier` set, one subscription, one StoreKit entitlement check cached on the Watch), but engineer every code path to assume `WCSession.isReachable == false` is the normal case, not the error case.
- **The prior research contains a direct internal contradiction about Watch timing, and the v1 side is the correct one.** _(high)_

### Recommendations
- [weeks] **Extract the active-session state machine into a Foundation-only SPM target (`SessionEngine`, `RestClock`, `SetLog`, `MergeResolver`) in week 1, before any Watch code exists, and unit-test it with Swift Testing exactly like the existing 4,706-line Intelligence/ layer.** — This is the only hard architectural precondition. Elos's equivalent logic is 647 lines of SwiftUI @State in Views/ActiveSessionView.swift and cannot be reused on watchOS at all. Doing it first costs ~1 week; retrofitting after both UIs exist costs 3–4. It also makes the session teardown ordering and the merge resolver testable, which is where the lost-workout bugs live.
- [weeks] **Ship the Watch app in v1 with exactly this scope: today's plan list, HKWorkoutSession start, prefilled weight×reps with one-tap log, crown edit, auto rest timer with haptic + ±15s + skip, finish→HKWorkout + effort score, launch recovery, and one complication. Explicitly exclude program building, exercise-library browsing, charts, supersets UI, plate calculator, Siri, and motion rep counting.** — The review complaint is binary — "no Apple Watch app." Strong and Gymaholic prove a small standalone logger is what people want; Hevy is criticised for a Watch app that is present but phone-tethered. Everything past the list above buys little rating and costs months. Realistic solo build: ~7–9 calendar weeks including the shared-engine week and ~2 weeks of device testing.
- [weeks] **Configure the Watch's SwiftData store as `ModelConfiguration(schema:, cloudKitDatabase: .none)` and treat WatchConnectivity `transferUserInfo` as the sole durable Watch→phone channel, with `updateApplicationContext` for the phone→Watch plan and ack-set, and `transferFile` for an end-of-session JSON backup.** — FB17685611 terminates a watch app 30–60s in when Always-On is off and the phone is unreachable — the exact basement-gym case. `updateApplicationContext` coalesces and would silently drop sets. `sendMessage` needs reachability. `transferUserInfo` is the only FIFO, reboot-surviving queue.
- [days] **Define the sync record now as `{ clientID: UUID (immutable, minted on the logging device), sessionClientID, exerciseInstanceID, setIndex, deviceID, revision: Int, loggedAtSessionOffset: TimeInterval, deleted: Bool }`, make every merge an idempotent upsert on `clientID`, resolve conflicts by `(revision, deviceID)` never by timestamp, and add `client_id UNIQUE` + tombstone columns to the backend schema on day one.** — Prior research verified the Elos backend has no sync protocol whatsoever — no version, cursor, tombstone or change feed on any workout table. A three-device topology (Watch, phone, server) makes retrofitting this far more expensive than the two-device case. Order-independence is required because the transferUserInfo queue does not survive a device restore.
- [hours] **Set `WKBackgroundModes = ["workout-processing"]` AND `UIBackgroundModes = ["audio"]` on the Watch target, and require an active HKWorkoutSession before arming any rest timer — including for users who decline heart-rate sharing.** — Background/Always-On haptics are blocked on watchOS except for apps with a live workout session (confirmed as-designed by Apple DTS). Without both keys and a live session the rest-end haptic silently does nothing when the wrist is down, which is the exact failure competitors get 1-starred for.
- [days] **Write session RPE — and per-exercise RPE via `HKWorkoutActivity` — into Apple's Training Load using `relateWorkoutEffortSample(_:with:activity:)`, and say so plainly in the App Store listing.** — It is the only meaningful strength-specific write HealthKit accepts, no science-lifting competitor ships it, it surfaces in Apple's own Fitness app, and the data is already collected (ElosSchema.swift:145,196-197). One day of work for a visible, defensible integration.
- [weeks] **Make the common logging path zero crown turns: prefill last session's weight×reps, put the whole set on one screen, bind `.handGestureShortcut(.primaryAction)` to "Log set" during a set and "Skip rest" during rest, and set the crown's `by:` to the resolved plate increment (2.5 kg / 5 lb) so one detent equals one plate.** — The prior UX teardown established that anything above ~3 taps per set loses. Crown-scrolling to 102.5 kg in 0.1 steps is the cramped-interface criticism levelled at Gymaholic. Double tap gives a one-handed, chalked-hands path no competitor advertises — but it needs Series 9+, so a tap equivalent must always exist.
- [weeks] **Budget 2 full weeks of on-device testing on real hardware (a Series 9 or later for double tap, plus an Ultra if you want the Action-button control), including at least six real gym sessions with the phone in a locker and airplane mode toggled mid-session.** — `transferUserInfo`/`transferFile` are unimplemented in the watchOS Simulator; background haptics work in the simulator and fail on device; Always-On, CPU-budget suspension, and arm64 numeric differences on Series 9+ only reproduce on hardware. This is the phase solo devs cut and then ship the exact bug the category is notorious for.
- [hours] **Wrap every `sendToRemoteWorkoutSession` call in a 3-second cancellable Task, use HealthKit mirroring only for live display ("in progress on Watch", current HR), and never let a mirroring send mark a set delivered.** — ~5% of workouts see the call hang with neither success nor error for the entire session, on watchOS 10/11 and iOS 17/18, with no Apple fix. If any correctness depends on it, 1 in 20 workouts breaks.
- [days] **Route session start through `healthStore.startWatchApp(toHandle: configuration)` when the user taps start on the phone, so the Watch is always the primary session owner and the phone is always the mirror; give the session record a `loggingDeviceID` and switch the non-authoritative device to a read-only "in progress" screen.** — Mirroring direction is fixed (Watch primary, iPhone mirrored) and cannot be inverted, so any design that treats the phone as primary fights the framework. A single explicit authority token prevents the double-logging class of bug; dedupe by clientID still backstops it when the advisory hand-off message is one of the 5% that hangs.
- [days] **Throttle Always-On rendering explicitly: scope the countdown to a `TimelineView(.periodic)` subview at 1 Hz normally and 10–20 s when `\.isLuminanceReduced`, render minutes-only in the reduced state, resolve animations to a rest frame, and profile with Instruments on device.** — An active workout session grants background runtime but the system still suspends on CPU-budget overrun — an Apple engineer attributed exactly this to a SwiftUI rewrite doing more per-tick work. A shipping watch app reached 12–16h battery by separating refresh schedules this way.
- [days] **Ship one `accessoryCircular`/`accessoryCorner` WidgetKit complication ("Push Day — Start") plus, if you own an Ultra, one `ControlWidget` for the Action button; defer RelevanceKit/Smart Stack relevance to v2.** — ClockKit is deprecated so WidgetKit is mandatory anyway, and APNs widget push now works on watchOS 26. The complication is the cheapest possible "this is a real Watch app" signal on the watch face. Whether third parties get a gym POI relevance context is unverified, so its payoff is speculative.

### Risks
- Energy for `.traditionalStrengthTraining` may be wrong at the framework level: developers report `HKLiveWorkoutBuilder` returning incorrect calories specifically for `traditionalStrengthTraining` and `jumpRope` on iOS 26 while walking/running are correct. If it persists on shipping watchOS 26, either the app displays wrong kcal or you hand-compute and diverge from Apple's Health data. Verify on device early; have a 'present as estimate' fallback in the design.
- Hardware dependency: double tap requires Series 9 / Ultra 2 or later, and every one of the load-bearing behaviours (background haptics, Always-On throttling, transferUserInfo, CPU-budget suspension, arm64 numerics) is untestable in the simulator. A solo dev without a modern Apple Watch cannot validate this feature at all.
- Scope creep from within: once the Watch target exists, every phone feature will look like it could go on the wrist. The competitors that lose here (Hevy) are the ones with a Watch app that is present but half-tethered; the ones that win (Strong, Gymaholic) are ruthlessly narrow. There is no defense against this except writing the exclusion list down before starting.
- Getting the sync merge wrong produces the single worst failure in this category — a lost workout — and it fails silently. Boostcamp, JuggernautAI, MacroFactor and RP all have documented lost-session reviews. The merge resolver must be unit-tested against interleaving, duplicate delivery, out-of-order delivery, and queue loss before any beta.
- Session teardown ordering is a hang, not a crash: awaiting `builder.endCollection` before `session.end()` never returns, and the user's finished workout evaporates. Apple's own sample and its async rewrite disagree on this. Cover it with an engine-level test rather than trusting the docs.
- FB17685611 is unfixed and the workaround (`cloudKitDatabase: .none`) means the Watch store cannot use CloudKit even later without re-testing. If a future requirement needs Watch-side CloudKit (e.g. a watch-first user with no iPhone), the architecture would need revisiting.
- Privacy-label exposure: health and fitness apps draw App Store review scrutiny, and requesting broader HealthKit read scopes than the features actually use is a common rejection cause. The Watch app's read set should be exactly heartRate + activeEnergyBurned + basalEnergyBurned + bodyMass, and the share set exactly workoutType + activeEnergyBurned + workoutEffortScore. Nothing speculative.
- Making any coaching claim from in-session heart rate during resistance training would be indefensible: HR during lifting reflects the pressor/Valsalva response and inter-set metabolite clearance, not aerobic intensity, and Apple Watch does not sample HRV during workouts at all. This is the same trap the prior research flagged for HRV — descriptive display only, never prescriptive.

### Open questions
- Do you own an Apple Watch Series 9 or later? Without one, double tap cannot be implemented or tested, and without any Apple Watch the entire feature is unbuildable. This is a hard gate on the plan, not a nice-to-have.
- Should the Watch app be gated behind the subscription, or free with the app? Strong and Hevy include it; gating it would neutralize the review-complaint benefit for free-tier users, who are the ones writing the reviews.
- Do you want cellular-model support in v1 — i.e. the Watch syncing directly to your backend with no phone present at all? This doubles the sync surface (auth token on Watch, keychain, retry policy) for a small user segment and is a clean v2 boundary, but the decision changes the backend auth design now.
- Is any user allowed to log on the phone while the Watch session is running, or does the Watch take exclusive logging authority for the session? Exclusive is far simpler and matches how mirroring works; permissive is friendlier but adds a whole class of merge conflicts.
- Should the Watch be able to start a free/unplanned workout, or only sessions already planned on the phone? Planned-only removes exercise search from the wrist entirely and cuts perhaps two weeks; free-workout support is the difference between 'companion' and 'standalone' for some users.
- What is the launch date target? If the app ships after September 2026, watchOS 27 will be current and watchOS 26.0 as the minimum covers current-and-one-back — comfortable. If you plan to ship well into 2027, revisit whether to move the floor to 27 (which buys nothing for strength, so probably not).
- Do you want to write per-exercise `HKWorkoutActivity` segments with custom metadata as a self-recovery backup, accepting that nothing else can read them, or keep HealthKit writes minimal (one workout + effort score) for a cleaner privacy story?
- Is a watch-face complication worth the extra target and provisioning complexity in v1, or is it acceptable to ship the Watch app in v1 and the complication in the first point release?
